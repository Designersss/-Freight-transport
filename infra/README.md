# Инфраструктура

RD-02: локальный PostgreSQL 17 и API. Скопируйте .env.example в .env и задайте непустой уникальный POSTGRES_PASSWORD; заполните DATABASE_URL (пароль в URL должен быть percent-encoded).

Пример структуры URL: postgresql://freight:YOUR_ENCODED_PASSWORD@127.0.0.1:5432/freight?connect_timeout=2&pool_timeout=2

```bash
docker compose up -d --wait postgres seaweedfs
pnpm install --frozen-lockfile
pnpm db:deploy
pnpm db:status
pnpm dev:api
```

Liveness: GET http://127.0.0.1:4000/api/v1/health.
Readiness: GET http://127.0.0.1:4000/api/v1/health/ready — 200 только при доступности мигрированной БД, иначе 503.

PostgreSQL доступен только через loopback. Том сохраняет данные. Не используйте docker compose down -v без осознанного удаления данных. Образ dev закреплён по major; production digest и резервирование — RD-18.

Интеграционный тест: задайте TEST_DATABASE_URL для отдельной одноразовой тестовой БД с применённой миграцией и запустите pnpm test:integration. CI использует одноразовый контейнер. Не используйте production URL. Миграции создают outbox_events и event_publications.

## Worker и очередь

В другом терминале после миграций: `pnpm dev:worker`. Worker создаёт служебную схему pg-boss в той же PostgreSQL, регистрирует очередь outbox-relay и запускает её при старте и каждую минуту. Лимит обработки — до 10 пакетов за задачу, размер пакета OUTBOX_BATCH_SIZE (100 по умолчанию). Повторные попытки выполняются pg-boss; будущие циклы подбирают оставшиеся события.

Бизнес-модули вызывают appendOutboxEvent внутри своей транзакции. Relay блокирует только выбранные строки через FOR UPDATE SKIP LOCKED и в той же транзакции создаёт запись event_publications с уникальным event_id и отмечает исходное событие processed_at. Повторы и конкурентные запуски не дублируют публикации. processed_at означает публикацию в БД, а не отправку Telegram или SSE; attempts отражает число успешных транзакционных обработок, не все неудачные попытки. Порядок доставки внешним потребителям, права доступа, retention и отдельные идемпотентные обработчики будут проектироваться при подключении SSE/уведомлений. Не обещаем exactly-once внешних эффектов.

pg-boss и его схема управляются worker при запуске; production-миграции служебной схемы и разделение прав требуют проверки перед развёртыванием.

Документация pg-boss: https://pgboss.io/introduction и https://pgboss.io/api/scheduling.

## Приватное файловое хранилище

SeaweedFS 4.51 (weed mini) и S3 SDK. Перед запуском заполните S3_ACCESS_KEY и S3_SECRET_KEY уникальными локальными значениями. S3_BUCKET создаётся при первом запуске, данные сохраняются в seaweed-data. Только S3-порт привязан к loopback; filer, volume, admin и WebDAV наружу не публикуются, сервис в отдельной сети Compose. При изменении ключей существующего тома требуется штатная ротация учётных данных SeaweedFS, а не простая замена .env.

Пакет @freight/storage предоставляет серверные put/get/delete/checkReadiness и проверку размера, MIME и начальной сигнатуры. Стартовая техническая политика: JPEG, PNG, PDF до 10 MiB, случайные UUID-ключи. Это предварительные ограничения, не окончательный продуктовый список. Сигнатура не заменяет проверку полного формата, антивирус или безопасную обработку изображений. Не публикуем URL объектов и не выдаём S3-ключи браузеру.

Публичных файловых HTTP-endpoint пока нет: авторизация пользователя, проверка companyId/владения, метаданные в БД, политика удаления/сирот, потоковая загрузка и финальная проверка форматов будут реализованы с соответствующими бизнес-модулями. Перед вызовом get/delete сервер обязан проверить доступ к объекту по метаданным; случайный ключ сам по себе не является разрешением. Проверка S3 пока отдельная от readiness API, так как API ещё не использует файлы.

Для тестов на одноразовом хранилище с установленными S3_*: pnpm --filter @freight/storage test:integration. CI проверяет реальные put/get/delete, запрет анонимного чтения и неправильных ключей. Перед production требуется ограниченная сервисная учётная запись, TLS/сетевая изоляция, резервирование и проверка восстановления. Не используйте production bucket для тестов.

Официальная документация: https://github.com/seaweedfs/seaweedfs/wiki/Quick-Start-with-weed-mini.

## OpenAPI и клиент

При NODE_ENV=development Swagger UI доступен на http://127.0.0.1:4000/docs/; JSON — /docs/openapi.json. В test и production эти маршруты не регистрируются. Не публиковать Swagger наружу через reverse proxy.

Контракт выводится из NestJS-декораторов: `pnpm api:generate` генерирует packages/client-api/openapi.json и src/generated/api.ts через Orval. Генерация не требует запущенной БД или сети (после установки зависимостей). Оба файла коммитятся; править их вручную нельзя. `pnpm api:check` повторяет генерацию и проверяет отсутствие изменений; CI проверяет соответствие контракта и клиента. TypeScript компилирует сгенерированный код; его стиль управляется Orval, поэтому Biome исключает только каталог generated.

Пакет @freight/client-api не зависит от React или NestJS. Для браузера используется относительный путь /api/v1 и same-origin fetch; для серверного клиента создаётся отдельный createApiFetch(origin) и передаётся в сгенерированную функцию. Типизированный ответ содержит status/data/headers; ошибки транспорта и неожиданный ответ требуют обработки на вызывающей стороне. Сессии, cookies, CSRF и авторизация будут реализованы в RD-04. Сейчас документированы только реальные liveness/readiness; бизнес-эндпоинты добавляются вместе с модулями, без фиктивных API.
