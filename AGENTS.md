# MOVARO — обязательные правила разработки

## Greenfield до первого production-релиза

Решение владельца от 27.11.2026: MOVARO создаётся с нуля. При замене требований удалять устаревшие реализации, поля, ветки совместимости и фикстуры прежнего контракта; не сохранять их ради гипотетических legacy-данных. Обновлять схему, API, UI, тесты и актуальную документацию согласованно. В незамёрженной ветке допускается пересобрать только её unreleased миграции для чистой тестовой БД. Миграции main, Git history и реальные/непроверенные БД не переписывать и не очищать автоматически. После первого production-релиза обязательны совместимые миграции и сохранность пользовательских данных. Quality/security gates и ручная приёмка неизменны.

- При каждом взаимодействии с проектом, включая анализ без изменений, первым делом прочитать [movaro-code-style](.agents/skills/movaro-code-style/SKILL.md). Навык обязателен независимо от области задачи; его применение и фактические результаты проверок указать в каждом отчёте. Перед отправкой изменений выполнить доступные локальные проверки по закреплённым настройкам; при недоступности явно зафиксировать блокер и использовать Draft PR для проверки, не считать gate пройденным.
- До изменения кода прочитать документацию официального API закреплённой версии и проверить реальные типы/peer dependencies. В PR указать ссылки и решения, а не только результат компиляции.
- SOLID, KISS, DRY; инкапсулировать состояние и инфраструктуру в сервисах, использовать DI и композицию. React — функциональные компоненты и хуки согласно документации, чистые функции для преобразований; не вводить классы ради классов.
- Внутренние ссылки — Next.js Link через next-intl createNavigation. Обычный anchor допустим для внешних URL и внутристраничных якорей. Использовать Image при подходящих сценариях, документированные server/client boundaries.
- UI — единая библиотека shadcn/ui; использовать официальный registry, не изобретать доступные примитивы без основания. Семантика, клавиатура, обе темы и RU/EN.
- Сервер: NestJS modules/providers/DI, Fastify API, Prisma транзакции, параметризованные запросы; права и границы компаний проверять на сервере. Не открывать маршруты без авторизации.
- Не ослаблять strict TypeScript, тесты, frozen lockfile, security/license checks. Не коммитить секреты и чужие данные. Не заявлять, что непроверенный код работает.
- До merge: review всех изменённых файлов, реальные тесты, CI и ручная приёмка владельца. Отдельно фиксировать открытые вопросы и технический долг.

## CI по контрольным точкам

- Во время реализации держать PR в Draft. На открытие, новые коммиты и повторное открытие PR запускаются Quick Checks: frozen install, OpenAPI/client, Biome lint и strict typecheck (Turbo может выполнять сборку). Полный набор тестов не запускается на обычный push.
- После завершения функционального этапа перевести Draft PR в Ready for review: это запускает полный CI с обязательным job `quality`. После появления workflow в main доступен также Actions → CI → Run workflow для выбранной ветки; ручной запуск не заменяет проверку merge-контекста PR, если GitHub её требует.
- При любых изменениях после начала приёмки вернуть PR в Draft до новых коммитов и снова перевести в Ready for review для полного CI на актуальном head/base. Не использовать зелёный результат старого SHA. Не запускать повторный полный CI без изменений, если актуальный результат уже подтверждён.
- Ручная приёмка владельца начинается только после успешного полного `quality` на актуальной версии. Merge требует полного CI, review, ручной приёмки и явного разрешения владельца. Защиту main не отключать; отсутствие `quality` во время Draft ожидаемо, Quick Checks его не заменяет. После merge в main полный CI запускается автоматически.
- Каждый workflow отменяет предыдущие незавершённые запуски своего типа на том же ref. Не использовать условно пропущенный job `quality`, skip ci или фиктивные статусы для обхода обязательной проверки. Локальные проверки по области изменений остаются обязательными при доступном окружении.

## Design Quality Gate (RD-03.1)

- Перед любой задачей UI/UX прочитать [DESIGN.md](DESIGN.md), [movaro-design](.agents/skills/movaro-design/SKILL.md), актуальные требования issue и существующие токены/компоненты. Утверждённые решения владельца важнее внешних рекомендаций; конфликт с доступностью или безопасностью явно эскалировать.
- Для внешних навыков использовать только изученные текстовые рекомендации и официальную документацию; не запускать сторонние установщики, бинарники или MCP и не передавать секреты. Новую зависимость или копирование стороннего кода согласовывать после проверки лицензии и закреплённой версии.
- Для UI PR приложить реальные результаты проверки по матрице dark/light, RU/EN, desktop/mobile, клавиатуре и состояниям; указать сравнение с референсом, отклонения и непроверенное. Скриншоты без персональных данных. Не заменять функциональные тесты визуальным ревью. Merge только после CI и ручной приёмки.

## Маршрутизация навыков MOVARO

Инструкции — собственные Markdown-файлы репозитория. При работе в ChatGPT их нужно прочитать из текущей ветки; автоматическая загрузка не предполагается. Не загружать все навыки без причины. Для UI всегда применять DESIGN.md, movaro-design и movaro-review; дополнительно выбирать навыки по таблице ниже. Для остальных PR применять movaro-review и релевантный инженерный навык.

Не менять согласованный стек, требования или CI из-за внешнего навыка.

## Backend & Architecture Quality Gate

Для серверной задачи прочитать docs/architecture.md, актуальный issue и текущий код; выбрать навыки ниже. movaro-backend и movaro-review обязательны при изменении серверного runtime; movaro-architecture — при изменении границ/инвариантов. movaro-security — при любом изменении доступа, tenant-данных, нового endpoint или доверенной границы. movaro-testing применяется для всех изменений поведения, movaro-performance — для измеряемых проблем скорости. Не загружать все навыки без причины.

В PR по backend указать бизнес-инварианты, права, транзакции/повторы, совместимость контрактов, миграции/восстановление и наблюдаемость по применимости. Приложить результаты реальных негативных, конкурентных, API и интеграционных тестов на актуальном commit; при недоступности стенда gate остаётся открытым. Не объявлять реализацию production-ready по одним инструкциям. Не ослаблять существующий quality CI; ручная приёмка и явное разрешение на merge обязательны. [Источники backend-навыков](docs/backend-skill-sources.md) — справочный реестр, не установленные пакеты.

## Обязательный отчёт о применении навыков (Skills Usage Report)

- В начале каждой задачи, включая проектирование, исправление, ревью и документацию, открыть актуальный AGENTS.md в рабочей ветке, определить применимые навыки по таблицам выше и прочитать их SKILL.md до реализации. При расширении scope пересмотреть выбор; перед итогом сверить требования с фактическим diff и результатами. Если ветка ещё не содержит согласованные навыки, использовать явно указанную актуальную ветку/commit с ними и зафиксировать источник. Не считать знание из предыдущего диалога доказательством чтения.
- В конце каждого содержательного отчёта владельцу (в том числе промежуточного среза) и в описании PR или комментарии к нему добавить раздел «Использованные навыки и источники». Для PR сохранять актуальный итог после новых изменений. Указывать только реально прочитанные файлы/разделы, ссылку на SKILL.md с ref/commit, статус (применён / изучен, но не потребовался / недоступен), конкретное правило и что оно изменило в коде, решении, тестах или ревью. Для проверок указать фактическое подтверждение: файл, diff, тест, CI или явно непроверенный результат.
- В том же разделе отдельно перечислить реально изученные внешние источники и документацию закреплённых версий, с URL и кратким объяснением использования. Не выдавать наличие ссылки в реестре за чтение источника. Если внешние источники не понадобились, указать это. Для обязательного навыка, который не удалось прочитать/применить, объяснить блокер и последствия; не заявлять соответствующий gate пройденным.
- Формат: таблица «Навык (ссылка/ref) | Статус | Что изучено и применено | Подтверждение»; затем «Внешние источники» и «Ограничения / неприменённые обязательные навыки». Для небольшой задачи допустим компактный список с теми же сведениями. Не перечислять все навыки ради количества. Отсутствие отчёта или неподтверждённое заявление о выполнении обязательных навыков — открытый пункт ручного review до merge; это процессное требование, не автоматическая CI-проверка.
