# RD-04 — пошаговая регистрация MOVARO

Статус: email-first согласован владельцем 27.11.2026; реализован в Draft PR #24, интеграционные и ручные проверки ещё не подтверждены. Связано с #5.

## Пользовательский сценарий

0. Выбор способа: две карточки email и Telegram, без счётчика шагов. Если Telegram-бот недоступен, карточка видима, но действие заблокировано с объяснением.
1. Email: ввод и проверка адреса, отправка одноразовой ссылки. Без счётчика шагов. До подтверждения нет аккаунта, пароля, роли, профиля или резерва username.
2. Подтверждение: переход на /ru|en/signup#token=..., удаление fragment из адресной строки, явное действие «Подтвердить почту». Ссылка действует 60 минут, чтение не потребляет её. Повторно открыть письмо после перезагрузки. Адрес нельзя менять после подтверждения.
3. Пароль (шаг 1 из 4): обязательная длина 6–128 символов, серверная валидация. Пароль и proof только в памяти формы, не в localStorage/sessionStorage. При переходе на другой email данные очищаются.
4. Роль (шаг 2 из 4): владелец компании, диспетчер или водитель. Активация карточки переводит на следующий шаг. До сохранения роль можно изменить через «Назад». PLATFORM_ADMIN отсутствует.
5. Профиль (шаг 3 из 4): обязательны имя, фамилия, полная дата рождения, для владельца — название компании. Ручной ввод даты и календарь синхронизируются. Нет фото, временной загрузки или поля возраста.
6. Username (шаг 4 из 4): сервер предлагает свободный вариант по имени и фамилии; пользователь может изменить его. Уникальность окончательно проверяется в БД. Конфликт username сохраняет подтверждение и ввод, чтобы выбрать другое имя.
7. Завершение: Better Auth создаёт пользователя и credential; PostgreSQL в той же транзакции потребляет proof и сохраняет профиль. Нет авто-входа. После успешного создания — переход на login. Существующий аккаунт никогда не заменяется.

Telegram использует согласованные три шага role → profile → username в едином серверном черновике после подтверждения Telegram identity. Пользователь может продолжить на сайте либо в чате. Завершение регистрации создаёт аккаунт, но не сессию: необходим свежий подтверждённый вход. Связанный Telegram нельзя отвязать или заменить.

## Визуальный контракт

Сохранить существующий AuthPanel, Manrope, семантические токены, компактную типографику, dark/light, RU/EN. После подтверждения личности шаги имеют понятные заголовки и индикатор фактического прогресса; «Назад» возвращает предыдущий шаг, сохраняя ввод в рамках текущей формы. Карточка роли — доступная кнопка с иконкой, названием, коротким описанием и стрелкой; без предвыбора, без второй кнопки. Переходы CSS opacity/transform по направлению навигации 220 мс, прогресс 250 мс, без задержки действий и с отключением необязательного движения при prefers-reduced-motion. Фокус на заголовке следующего шага, Tab/Enter/Space, видимый фокус. Без новых библиотек, без изменения общих токенов. Точные отступы/время анимации — предложенные, проверить в браузере.

## Технические границы

- Публичные POST endpoints: registration/email/start, read, complete. Complete принимает token/password/registration, не email. Ссылка доставляется через SMTP, token в БД только в виде SHA-256 digest.
- Start ограничен отдельной квотой verification, read и complete — собственными квотами. Существующий email не раскрывается до доказательства владения почтой. Существующие аккаунты не заменяются. При откате транзакции proof остаётся доступен; повтор после commit не создаёт дубликат.
- Нет прежнего email-черновика регистрации и публичных signup/verify/resend endpoints. Telegram использует отдельный общий черновик. Миграция удаляет старое поле без переписывания истории и останавливается, если в БД есть непустые старые черновики. Реальные БД автоматически не сбрасываются.
- Компания как домен и членство — RD-05; название пока данные профиля владельца, не фиктивная компания.
- Фото доступно только в настройках после подтверждения email и входа (UI, HTTP и SQL ограничение реализовано в P2.01; фактические интеграционные проверки ещё впереди).
- Production gate закрыт до полного quality и ручной приёмки.

## Приёмка

Реальный сценарий email → письмо → подтверждение в другом браузере → password → role → profile → username → login. Проверить все три роли, возврат, expiry/replay, ошибку и повтор отправки, конкурентный complete, rollback при конфликте, отсутствие user/session до complete и автоматической сессии после, запрет admin/смены роли, отсутствие фото при регистрации. Отдельно проверить Telegram-черновик, смену канала, завершение и последующий вход, управление сессиями, восстановление пароля и настройки. RU/EN × dark/light × desktop/mobile, клавиатура и reduced motion; axe/overflow, PostgreSQL и SMTP, storage integration tests. Никаких production-заглушек. Полный quality CI и ручная приёмка владельца обязательны.
