# RD-04 — пошаговая регистрация MOVARO

Статус: требования владельца от 27.11.2026, технический сценарий предложен для согласования. Связано с #5 и PR #24. Текущая одноэкранная форма профиля подлежит замене, не является финальной визуальной приёмкой.

## Пользовательский сценарий

1. Учётные данные: email, пароль; проверка формата и согласованной длины. Имя переносится на шаг профиля. Продолжить.
2. Выбор роли: три самостоятельные карточки «Владелец компании», «Диспетчер», «Водитель». Активация карточки мышью, touch или клавиатурой немедленно переводит на следующий шаг; отдельной кнопки продолжения нет. Роль до финального сохранения можно изменить через «Назад». PLATFORM_ADMIN отсутствует.
3. Профиль: имя и фамилия обязательны для всех. Владелец указывает название компании. Водитель и диспетчер могут указать возраст и выбрать фото. Возраст и фото необязательны, как в прежних решениях для водителя; необязательность возраста диспетчера — предложенная интерпретация нового требования. Фото можно удалить/заменить до сохранения. Продолжить.
4. Username: обязательный уникальный @username для каждого пользователя. Сервер предлагает свободный вариант на основе имени и фамилии; пользователь может изменить его или нажать «Продолжить» и принять предложенный. Проверка доступности и окончательное сохранение выполняются сервером. Отдельный экран username — предлагаемая компоновка.
5. Подтверждение почты по ссылке остаётся обязательным. Предлагаем отправлять письмо после завершения формы, сохранять данные регистрации на сервере и после подтверждения/входа восстанавливать профиль без повторного ввода. При неподтверждённой почте вход запрещён и открывается экран подтверждения. Не выдавать сессию до проверки email. Если пользователь уже зарегистрирован, но не закончил профиль, при входе продолжить с недостающего шага.

## Визуальный контракт

Сохранить существующий AuthPanel, Manrope, семантические токены, компактную типографику, dark/light, RU/EN. Шаги имеют понятные заголовки и индикатор фактического прогресса; «Назад» возвращает предыдущий шаг, сохраняя ввод в рамках текущей формы. Карточка роли — доступная кнопка с иконкой, названием, коротким описанием и стрелкой; без предвыбора, без второй кнопки. Переходы CSS opacity/transform, ориентир 180–220 мс, без задержки действий и с отключением необязательного движения при prefers-reduced-motion. Фокус на заголовке следующего шага, Tab/Enter/Space, видимый фокус. Без новых библиотек, без изменения общих токенов. Точные отступы/время анимации — предложенные, проверить в браузере.

## Технические границы и вопросы

- Текущий signup требует name; текущий profile endpoint разрешён только подтверждённой сессии, возраст хранится в driver_age с ограничением DRIVER. Не переносить выдачу роли в клиент и не разрешать создание активного профиля без подтверждения. Нужно согласовать и реализовать серверный черновик регистрации, связанный с конкретным account id, или эквивалентный атомарный механизм Better Auth. Проверить повторы signup, конкурентные запросы, отсутствие сессии, запрет admin, ошибку SMTP и восстановление незавершённого сценария. Не хранить пароль в localStorage/sessionStorage/URL; Better Auth выполняет хеширование.
- Название компании — новое требование RD-04 к сбору данных, ранее данные компании относились к RD-05. Предлагается хранить название как данные незавершённого создания компании; не создавать фиктивное членство или готовую компанию до реализации домена RD-05. Полный процесс компании остаётся RD-05.
- Миграция возраста должна сохранить существующие значения driver_age и обеспечить допустимость возраста для DRIVER/DISPATCHER, не для других ролей. Пределы возраста согласуются отдельно; не вводить бизнес-ограничение без основания.
- photoKey уже есть, но API загрузки профиля ещё нет. Реализовать действительную приватную загрузку JPEG/PNG с проверкой содержимого, лимитом размера, полномочиями, очисткой брошенных файлов и безопасным чтением. При выборе фото до подтверждения требуется защищённая ограниченная временная загрузка, привязанная к регистрации, без выдачи рабочей сессии; альтернатива — подтверждение email перед выбором роли и загрузка только после входа. До проверки этой границы не выдавать сохранение фото за реализованное. Не хранить произвольный URL/photoKey из клиента.
- Действующий API с одноразовым выбором роли и серверными гарантиями сохранить или мигрировать с обратной совместимостью. Не открывать production gate. Telegram следует тому же сценарию профиля, без повторного создания аккаунта.

## Приёмка

Реальный браузерный сценарий email → role → role-specific profile → username → verification → login → восстановление сохранённого профиля. Все три роли, возврат назад, повтор/ошибка отправки, перезагрузка/новый браузер после регистрации, запрет смены роли и администратора, отказ неподтверждённой сессии, безопасная загрузка и удаление фото. RU/EN × dark/light × desktop/mobile, клавиатура и reduced motion; axe/overflow, реальный PostgreSQL и SMTP, реальные storage integration tests. Не использовать production-заглушки. Существующий обязательный quality CI и ручная приёмка владельца.

## Срез 1 — совместимое расширение профиля

Новая additive Prisma/SQL миграция 20261127050000_registration_profile_fields добавляет nullable company_name, расширяет CHECK driver_age на DRIVER и DISPATCHER, запрещает company_name у иных ролей, пустые и длиннее 200 символов названия. Существующие данные и роль не изменяются. В API сохранено техническое имя driverAge для совместимости; это возраст водителя или диспетчера. GET/POST /profile возвращает companyName (null у старых профилей), разрешает ввод только владельцу. Для будущего wizard отдельная registrationProfileInput требует название компании у владельца, legacy профиль может быть без него. Компания/членство не создаются. Длина названия до 200 — предложенный технический предел, возраст положительный PostgreSQL integer, без новой бизнес-границы. Проверки схемы расширены на реальные ограничения, HTTP-тест на запрещённые поля и конкурентный выбор с возрастом диспетчера, существующий browser E2E на новый DTO. Новые поля пока не подключены к старому UI. Новая регистрация до подтверждения, черновик, фото и анимации ещё не реализованы. Предыдущие миграции не редактировались; fresh migration и тесты должны пройти CI, upgrade с заполненными данными проверяется отдельно до production.

Для следующего среза рассмотрен Better Auth 1.7.28 additionalFields: signup валидирует и сохраняет дополнительные поля при создании пользователя, существующий email получает synthetic response без обновления, письмо отправляется после транзакции. Предлагается хранить только валидированный черновик без пароля и секретов на записи пользователя, не отдавать его в публичных ответах и материализовать профиль атомарно после подтверждённого входа. Механизм ещё не реализован; проверить обработку ошибок, конкурентность, повторный signup и привязку к реальному user id. Источник: https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/api/routes/sign-up.ts .

## Уникальный username — дополнение владельца от 27.11.2026

Требование: уникальный @username для каждого пользователя независимо от роли. Имена и фамилии не уникальны. При регистрации предложить свободный вариант из имени и фамилии, разрешить ручной выбор или принятие автоматически предложенного варианта. Telegram и email относятся к одной внутренней идентичности, отдельного username на компанию или способ входа нет.

Предлагаемые технические правила (не считать утверждёнными все параметры):

- Глобальный namespace, нормализация в lowercase; @ — отображаемый префикс, не часть хранимого значения. Предлагаемый формат 3–32 символа, a–z, 0–9 и подчёркивание, первая буква латинская. Транслитерация имени/фамилии для кириллицы и других поддерживаемых имён, очистка и ограничение длины, безопасный нейтральный вариант если результат пустой. При занятости — ограниченный подбор суффиксов 2, 3 и далее, затем случайный суффикс; без email, телефона или даты рождения. Проверить реальные правила транслитерации и длину до реализации.
- Предлагаемый отдельный четвёртый экран: автоподстановка, ручное редактирование, проверка после короткого debounce, отмена/игнорирование устаревших запросов, локализованные состояния «Проверяем», «Свободно», «Занято», ошибка сети. Не заменять введённый вручную username при возврате к имени. Свободный вариант не является гарантией бронирования.
- Хранить канонический username в едином namespace, связанном с неизменяемым user id; окончательный механизм выбрать вместе с черновиком регистрации. Единственное DB UNIQUE ограничение должно охватывать и принятые регистрации до подтверждения, и действующие аккаунты; не делать две несогласованные уникальности по таблицам. На финальном запросе атомарное назначение, при конфликте предложить другой вариант, сохранить поля и не создавать дубликат аккаунта. Не доверять клиентскому результату availability, не обновлять существующую учётную запись по email или username.
- Для неподтверждённых аккаунтов определить ограниченное по времени удержание имени и политику очистки/восстановления так, чтобы не допустить захвата чужого аккаунта или массовой блокировки имён. Ограничить публичные проверки доступности и signup по частоте; возвращать только доступность/вариант, без email, user id, роли, статуса и прочих личных данных. Зарезервированные системные имена (admin, support, movaro и подобные) — предлагаемый список, согласовать перед реализацией.
- Для старых аккаунтов добавить совместимую миграцию и назначение уникального username без потери профилей. Для глобального администратора назначать только защищённой серверной командой. Пользовательский поиск, если реализуется в следующих модулях, обязан соблюдать существующие права и границы компаний; username не даёт доступ к чужим данным. Вход остаётся email/пароль или Telegram, вход по username не добавляется автоматически.
- Решение владельца от 27.11.2026: пользователь может менять username в настройках профиля не чаще одного раза в неделю. Предлагаемое техническое толкование — скользящие семь суток (168 часов) с момента успешной смены, серверное время UTC; первый выбор при регистрации не является сменой. Неуспешная попытка, занятое имя и повтор того же канонического значения не расходуют лимит. При ограничении интерфейс показывает дату следующего допустимого изменения. Проверка владения аккаунтом, cooldown и глобальная уникальность выполняются атомарно на сервере, одновременно допускается только одна успешная смена. Внутренние связи, права и ссылки на ресурсы используют неизменяемый user id, а не изменяемое имя. Политика повторного использования старого имени и сроки удержания неподтверждённых имён остаются открытыми.
- Дополнительная приёмка настроек: первая смена, повтор до истечения 168 часов, точная граница срока, занятый username, повтор того же имени, конкурентные запросы одного пользователя, отказ чужой/отозванной сессии, сохранение связей, корректное отображение даты в локали и на мобильном. Реализация и тесты ещё не выполнены.

Приёмка: одинаковые ФИО дают разные username, проверка регистра, ручной выбор и сохранение предложенного, недопустимые/зарезервированные имена, два независимых конкурентных signup с одним username, сохранение полей при конфликте и сетевой ошибке, повторный signup не перезаписывает чужие данные, восстановление после подтверждения из другого браузера/PWA, legacy и Telegram. RU/EN, dark/light, desktop/mobile, клавиатура и доступное текстовое состояние проверки. Реализация username пока открыта; этот документ не добавляет колонку, endpoint или UI.

## Срез 2 — серверный черновик регистрации и назначение username

В dev/test API существующий POST /sign-up/email принимает необязательное registration: { profile, username } поверх прежних email/password/name/locale. Строгие схемы, имя Better Auth формируется из профиля на сервере; legacy-запрос без registration поддерживается до замены UI. Username канонизируется в lowercase, 3–32 ASCII символа, первая буква латинская; admin/support/movaro запрещены. Это выбранные технические defaults предыдущего предложения. Prisma migration добавляет nullable username с единственным глобальным UNIQUE и CHECK, а также nullable registrationDraft (JSON в TEXT через Better Auth additionalFields, только профиль, без пароля, секретов и фото). Оба поля скрыты в Better Auth response. Signup сохраняет их в той же записи пользователя при создании; пароль хеширует Better Auth, email нормализуется. Письмо отправляется после транзакции. До подтверждения нет сессии и активного профиля. При успешном подтверждённом sign-in короткая транзакция блокирует запись пользователя, читает/валидирует черновик, создаёт профиль и очищает черновик. Повторный вход не создаёт второй профиль. При конфликте/сбое транзакция откатывается, cookie успешного входа не передаётся клиенту; возможная уже созданная невыданная сессия живёт до expiry, очистку проверить отдельно.

Username uniqueness проверяется БД при создании; precheck и postcheck после гонки возвращают 409 USERNAME_TAKEN без раскрытия владельца. Существующий mail limiter применяется прежде проверки, поэтому попытка с занятым username расходует квоту проверки email; улучшить UX отдельным rate-limited availability endpoint. Повторный signup с существующим email не перезаписывает данные, Better Auth сохраняет opaque success при свободном username. Не обещать полного отсутствия enumeration до threat-model и негативных тестов. Не реализованы: генерация/availability, получение username в публичном DTO, смена имени раз в неделю, backfill legacy, срок удержания и очистка неподтверждённых аккаунтов/освобождённых имён, фото, новый wizard, production activation. Новая миграция не меняет прежние данные; upgrade отдельно проверить.

Источники: https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/api/routes/sign-up.ts ; https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/db/schema.ts .

## Срез 3 — генерация и проверка username

Dev/test POST /api/v1/auth/username и Web bridge /api/auth/username принимают strict discriminated union: {action:"suggest", firstName, lastName} возвращает {username}; {action:"check", username} возвращает только {available:boolean}. Требуются точный origin, JSON без query и доверенный IP Fastify. Нет выдачи owner id, email или роли. Русская кириллица транслитерируется по собственному техническому правилу, латинские диакритики нормализуются NFKD, остальные символы очищаются, fallback user; это не универсальный транслитератор всех письменностей. Один параметризованный SELECT ANY проверяет до 13 вариантов: базовый, 2–10, три случайных суффикса; если все заняты, 503. Проверка не резервирует username, UNIQUE при signup остаётся обязательным. Зарезервированные и недопустимые имена возвращают 400. Лимит 60/min на доверенный IP и 600/min глобально (предварительные технические значения) отдельными username:* buckets в существующей таблице auth_mail_rate_limits; общий transactional helper, очистка изолирована по namespace, квота почты не расходуется. За текущим Web proxy IP общий, production требует проверенной топологии доверенных прокси и защиты от перечисления/нагрузки. Тесты расширяют реальный сценарий проверками кириллицы, диакритик, fallback, регистра, занятого имени, суффикса и конкурентного 429. UI, смена имени, старые аккаунты, срок резерва и фото остаются открытыми. Не меняли миграции, зависимости и production gate.

Реальный browser auth E2E дополнен вызовами suggest/check через Web proxy до регистрации. Негативные проверки включают недопустимый origin, GET и лишние поля. Функциональный результат нового CI ещё не подтверждён.
