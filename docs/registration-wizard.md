# RD-04 — пошаговая регистрация MOVARO

Статус: требования владельца от 27.11.2026, технический сценарий предложен для согласования. Связано с #5 и PR #24. Текущая одноэкранная форма профиля подлежит замене, не является финальной визуальной приёмкой.

## Пользовательский сценарий

1. Учётные данные: email, пароль; проверка формата и согласованной длины. Имя переносится на шаг профиля. Продолжить.
2. Выбор роли: три самостоятельные карточки «Владелец компании», «Диспетчер», «Водитель». Активация карточки мышью, touch или клавиатурой немедленно переводит на следующий шаг; отдельной кнопки продолжения нет. Роль до финального сохранения можно изменить через «Назад». PLATFORM_ADMIN отсутствует.
3. Профиль: имя, фамилия и полная дата рождения обязательны для всех трёх публичных ролей. Владелец указывает название компании. Водитель и диспетчер могут выбрать необязательное фото, удалить/заменить его до сохранения. Дата рождения вместо возраста — решение владельца от 27.11.2026, отменяет прежнюю необязательность возраста. Ручной ввод и календарь синхронизируются. Продолжить.
4. Username: обязательный уникальный @username для каждого пользователя. Сервер предлагает свободный вариант на основе имени и фамилии; пользователь может изменить его или нажать «Продолжить» и принять предложенный. Проверка доступности и окончательное сохранение выполняются сервером. Отдельный экран username — предлагаемая компоновка.
5. Подтверждение почты по ссылке остаётся обязательным. Предлагаем отправлять письмо после завершения формы, сохранять данные регистрации на сервере и после подтверждения/входа восстанавливать профиль без повторного ввода. При неподтверждённой почте вход запрещён и открывается экран подтверждения. Не выдавать сессию до проверки email. Если пользователь уже зарегистрирован, но не закончил профиль, при входе продолжить с недостающего шага.

## Визуальный контракт

Сохранить существующий AuthPanel, Manrope, семантические токены, компактную типографику, dark/light, RU/EN. Шаги имеют понятные заголовки и индикатор фактического прогресса; «Назад» возвращает предыдущий шаг, сохраняя ввод в рамках текущей формы. Карточка роли — доступная кнопка с иконкой, названием, коротким описанием и стрелкой; без предвыбора, без второй кнопки. Переходы CSS opacity/transform, ориентир 180–220 мс, без задержки действий и с отключением необязательного движения при prefers-reduced-motion. Фокус на заголовке следующего шага, Tab/Enter/Space, видимый фокус. Без новых библиотек, без изменения общих токенов. Точные отступы/время анимации — предложенные, проверить в браузере.

## Технические границы и вопросы

- Текущий signup требует name; текущий profile endpoint разрешён только подтверждённой сессии, дата рождения обязательна в профиле. Не переносить выдачу роли в клиент и не разрешать создание активного профиля без подтверждения. Нужно согласовать и реализовать серверный черновик регистрации, связанный с конкретным account id, или эквивалентный атомарный механизм Better Auth. Проверить повторы signup, конкурентные запросы, отсутствие сессии, запрет admin, ошибку SMTP и восстановление незавершённого сценария. Не хранить пароль в localStorage/sessionStorage/URL; Better Auth выполняет хеширование.
- Название компании — новое требование RD-04 к сбору данных, ранее данные компании относились к RD-05. Предлагается хранить название как данные незавершённого создания компании; не создавать фиктивное членство или готовую компанию до реализации домена RD-05. Полный процесс компании остаётся RD-05.
- Обязательная дата рождения для COMPANY_OWNER/DISPATCHER/DRIVER при регистрации email или Telegram; числового возраста в модели нет. Минимальный возраст и редактирование даты после регистрации пока не согласованы.
- photoKey уже есть, но API загрузки профиля ещё нет. Реализовать действительную приватную загрузку JPEG/PNG с проверкой содержимого, лимитом размера, полномочиями, очисткой брошенных файлов и безопасным чтением. При выборе фото до подтверждения требуется защищённая ограниченная временная загрузка, привязанная к регистрации, без выдачи рабочей сессии; альтернатива — подтверждение email перед выбором роли и загрузка только после входа. До проверки этой границы не выдавать сохранение фото за реализованное. Не хранить произвольный URL/photoKey из клиента.
- Действующий API с одноразовым выбором роли и серверными гарантиями сохранить или мигрировать с обратной совместимостью. Не открывать production gate. Telegram следует тому же сценарию профиля, без повторного создания аккаунта.

## Приёмка

Реальный браузерный сценарий email → role → role-specific profile → username → verification → login → восстановление сохранённого профиля. Все три роли, возврат назад, повтор/ошибка отправки, перезагрузка/новый браузер после регистрации, запрет смены роли и администратора, отказ неподтверждённой сессии, безопасная загрузка и удаление фото. RU/EN × dark/light × desktop/mobile, клавиатура и reduced motion; axe/overflow, реальный PostgreSQL и SMTP, реальные storage integration tests. Не использовать production-заглушки. Существующий обязательный quality CI и ручная приёмка владельца.

## Уникальный username — дополнение владельца от 27.11.2026

Требование: уникальный @username для каждого пользователя независимо от роли. Имена и фамилии не уникальны. При регистрации предложить свободный вариант из имени и фамилии, разрешить ручной выбор или принятие автоматически предложенного варианта. Telegram и email относятся к одной внутренней идентичности, отдельного username на компанию или способ входа нет.

Предлагаемые технические правила (не считать утверждёнными все параметры):

- Глобальный namespace, нормализация в lowercase; @ — отображаемый префикс, не часть хранимого значения. Предлагаемый формат 3–32 символа, a–z, 0–9 и подчёркивание, первая буква латинская. Транслитерация имени/фамилии для кириллицы и других поддерживаемых имён, очистка и ограничение длины, безопасный нейтральный вариант если результат пустой. При занятости — ограниченный подбор суффиксов 2, 3 и далее, затем случайный суффикс; без email, телефона или даты рождения. Проверить реальные правила транслитерации и длину до реализации.
- Предлагаемый отдельный четвёртый экран: автоподстановка, ручное редактирование, проверка после короткого debounce, отмена/игнорирование устаревших запросов, локализованные состояния «Проверяем», «Свободно», «Занято», ошибка сети. Не заменять введённый вручную username при возврате к имени. Свободный вариант не является гарантией бронирования.
- Хранить канонический username в едином namespace, связанном с неизменяемым user id; окончательный механизм выбрать вместе с черновиком регистрации. Единственное DB UNIQUE ограничение должно охватывать и принятые регистрации до подтверждения, и действующие аккаунты; не делать две несогласованные уникальности по таблицам. На финальном запросе атомарное назначение, при конфликте предложить другой вариант, сохранить поля и не создавать дубликат аккаунта. Не доверять клиентскому результату availability, не обновлять существующую учётную запись по email или username.
- Для неподтверждённых аккаунтов определить ограниченное по времени удержание имени и политику очистки/восстановления так, чтобы не допустить захвата чужого аккаунта или массовой блокировки имён. Ограничить публичные проверки доступности и signup по частоте; возвращать только доступность/вариант, без email, user id, роли, статуса и прочих личных данных. Зарезервированные системные имена (admin, support, movaro и подобные) — предлагаемый список, согласовать перед реализацией.
- Для старых аккаунтов добавить совместимую миграцию и назначение уникального username без потери профилей. Для глобального администратора назначать только защищённой серверной командой. Пользовательский поиск, если реализуется в следующих модулях, обязан соблюдать существующие права и границы компаний; username не даёт доступ к чужим данным. Вход остаётся email/пароль или Telegram, вход по username не добавляется автоматически.
- Решение владельца от 27.11.2026: пользователь может менять username в настройках профиля не чаще одного раза в неделю. Предлагаемое техническое толкование — скользящие семь суток (168 часов) с момента успешной смены, серверное время UTC; первый выбор при регистрации не является сменой. Неуспешная попытка, занятое имя и повтор того же канонического значения не расходуют лимит. При ограничении интерфейс показывает дату следующего допустимого изменения. Проверка владения аккаунтом, cooldown и глобальная уникальность выполняются атомарно на сервере, одновременно допускается только одна успешная смена. Внутренние связи, права и ссылки на ресурсы используют неизменяемый user id, а не изменяемое имя. Политика повторного использования старого имени и сроки удержания неподтверждённых имён остаются открытыми.
- Дополнительная приёмка настроек: первая смена, повтор до истечения 168 часов, точная граница срока, занятый username, повтор того же имени, конкурентные запросы одного пользователя, отказ чужой/отозванной сессии, сохранение связей, корректное отображение даты в локали и на мобильном. Реализация и тесты ещё не выполнены.

Приёмка: одинаковые ФИО дают разные username, проверка регистра, ручной выбор и сохранение предложенного, недопустимые/зарезервированные имена, два независимых конкурентных signup с одним username, сохранение полей при конфликте и сетевой ошибке, повторный signup не перезаписывает чужие данные, восстановление после подтверждения из другого браузера/PWA, Telegram. RU/EN, dark/light, desktop/mobile, клавиатура и доступное текстовое состояние проверки. Реализация username пока открыта; этот документ не добавляет колонку, endpoint или UI.

## Срез 2 — серверный черновик регистрации и назначение username

В dev/test API существующий POST /sign-up/email принимает необязательное registration: { profile, username } поверх прежних email/password/name/locale. Строгие схемы, имя Better Auth формируется из профиля на сервере; текущий незавершённый UI ещё использует запрос без registration; удалить этот путь при реализации wizard, не сохранять как legacy API. Username канонизируется в lowercase, 3–32 ASCII символа, первая буква латинская; admin/support/movaro запрещены. Это выбранные технические defaults предыдущего предложения. Prisma migration добавляет nullable username с единственным глобальным UNIQUE и CHECK, а также nullable registrationDraft (JSON в TEXT через Better Auth additionalFields, только профиль, без пароля, секретов и фото). Оба поля скрыты в Better Auth response. Signup сохраняет их в той же записи пользователя при создании; пароль хеширует Better Auth, email нормализуется. Письмо отправляется после транзакции. До подтверждения нет сессии и активного профиля. При успешном подтверждённом sign-in короткая транзакция блокирует запись пользователя, читает/валидирует черновик, создаёт профиль и очищает черновик. Повторный вход не создаёт второй профиль. При конфликте/сбое транзакция откатывается, cookie успешного входа не передаётся клиенту; возможная уже созданная невыданная сессия живёт до expiry, очистку проверить отдельно.

Username uniqueness проверяется БД при создании; precheck и postcheck после гонки возвращают 409 USERNAME_TAKEN без раскрытия владельца. Существующий mail limiter применяется прежде проверки, поэтому попытка с занятым username расходует квоту проверки email; улучшить UX отдельным rate-limited availability endpoint. Повторный signup с существующим email не перезаписывает данные, Better Auth сохраняет opaque success при свободном username. Не обещать полного отсутствия enumeration до threat-model и негативных тестов. Не реализованы: генерация/availability, получение username в публичном DTO, смена имени раз в неделю, срок удержания и очистка неподтверждённых аккаунтов/освобождённых имён, фото, новый wizard, production activation. Действует greenfield-правило AGENTS.md; промежуточные unreleased схемы не сохраняем.

Источники: https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/api/routes/sign-up.ts ; https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/db/schema.ts .

## Срез 3 — генерация и проверка username

Dev/test POST /api/v1/auth/username и Web bridge /api/auth/username принимают strict discriminated union: {action:"suggest", firstName, lastName} возвращает {username}; {action:"check", username} возвращает только {available:boolean}. Требуются точный origin, JSON без query и доверенный IP Fastify. Нет выдачи owner id, email или роли. Русская кириллица транслитерируется по собственному техническому правилу, латинские диакритики нормализуются NFKD, остальные символы очищаются, fallback user; это не универсальный транслитератор всех письменностей. Один параметризованный SELECT ANY проверяет до 13 вариантов: базовый, 2–10, три случайных суффикса; если все заняты, 503. Проверка не резервирует username, UNIQUE при signup остаётся обязательным. Зарезервированные и недопустимые имена возвращают 400. Лимит 60/min на доверенный IP и 600/min глобально (предварительные технические значения) отдельными username:* buckets в существующей таблице auth_mail_rate_limits; общий transactional helper, очистка изолирована по namespace, квота почты не расходуется. За текущим Web proxy IP общий, production требует проверенной топологии доверенных прокси и защиты от перечисления/нагрузки. Тесты расширяют реальный сценарий проверками кириллицы, диакритик, fallback, регистра, занятого имени, суффикса и конкурентного 429. UI, смена имени, старые аккаунты, срок резерва и фото остаются открытыми. Не меняли миграции, зависимости и production gate.

Реальный browser auth E2E дополнен вызовами suggest/check через Web proxy до регистрации. Негативные проверки включают недопустимый origin, GET и лишние поля. Функциональный результат нового CI ещё не подтверждён.

## Срез 4 — серверная смена username

Dev/test GET/POST /api/v1/auth/username/settings, Web bridge /api/auth/username/settings. GET возвращает {username, nextChangeAt} (null у незавершённого текущего сценария без имени, null даты если смена разрешена); POST принимает строго {username}, возвращает тот же DTO. Внутренний session id из Better Auth get-session с disableRefresh проверяется вместе с verified email, отсутствием draft и активным публичным профилем. Общий helper авторизации используется также в /profile; публичный session DTO не расширен. POST точный origin, JSON без query. Транзакция SELECT FOR UPDATE блокирует пользователя, профиль и сессию, повторно проверяет eligibility и время БД, изменяет только username и серверный timestamp. Additive migration username_changed_at TIMESTAMPTZ(6) + CHECK, интервал именно 168 hours, не календарные дни. Первое назначение не расходует лимит; повтор того же канонического имени возвращает текущее состояние, занятое имя UNIQUE -> 409 USERNAME_TAKEN без изменения cooldown. Конкурентная смена -> 409 USERNAME_CHANGE_COOLDOWN + ISO UTC nextChangeAt, отказ не расходует лимит. В dev/test прежнее имя освобождается при UPDATE; это временное техническое поведение, окончательная политика повторного использования/резерва ещё не согласована и блокирует production. Пользовательский поиск и ссылки по username ещё не открыты. Смена не изменяет user id, role, связи или сессии. Тесты: first assignment через реальный Web/API, no-op, занятость, конкуренция, отказ в cooldown, истечение 168 часов через изолированные данные, профиль сохранён, anonymous/deactivated/revoked/лишнее поле. UI настроек, Telegram, аудит и окончательный lifecycle имён остаются открытыми. Production gate сохранён.

## Срез 5.1 — приватное хранилище фото профиля

В существующем @freight/storage добавлены putProfilePhoto/getProfilePhoto, использующие тот же SeaweedFS S3, непрозрачный ключ, таймаут и проверку сигнатуры. Предлагаемый технический лимит — 2 MiB на файл (после клиентского уменьшения, если понадобится), только JPEG/PNG. Общий лимит документов 10 MiB и PDF не изменены. Ограничение чтения фото действует и по ContentLength, и при накоплении потока. Негативные unit-тесты и интеграция на реальном SeaweedFS проверяют размер, тип, сигнатуру, приватный объект, удаление, запрет PDF через фото-интерфейс и превышение лимита при чтении. Объекты не выдаются анонимно, HTTP endpoint и профиль пока не подключены. Проверка сигнатуры не доказывает полноценную декодируемость изображения. До пользовательского upload необходимо определить проверенный декодер/перекодирование с лимитами размеров изображения и ресурсов, удаление EXIF, права, quota, обработку отказов/конкурентной замены и уборку orphan объектов. Не добавлять новый декодер без проверки версии/лицензии и согласования. Для фото до подтверждения email — отдельный ограниченный протокол временной загрузки с TTL, привязкой к регистрации и очисткой; альтернативно загрузка после подтверждённого входа с явным согласованием UX. Не добавлять публичную загрузку без защищённой границы. Нет новых зависимостей, миграций, API или изменений CI; production gate сохранён.

Источники: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html ; AWS SDK 3.922.0 https://github.com/aws/aws-sdk-js-v3/blob/v3.922.0/clients/client-s3/src/commands/PutObjectCommand.ts и https://github.com/aws/aws-sdk-js-v3/blob/v3.922.0/clients/client-s3/src/commands/GetObjectCommand.ts .

## Срез требований — обязательная дата рождения (27.11.2026)

Решение владельца: вместо числового возраста собирать полную дату рождения у всех пользователей, ручной ввод и календарный picker работают в обе стороны. Обязательность для трёх публичных ролей и обоих способов регистрации; глобальный администратор по-прежнему создаётся защищённой командой, его дополнительные поля уточнить отдельно. Фото остаётся необязательным. Числовой возраст полностью исключён из актуальной модели.

Предлагаемая реализация: birthDate в API/черновике как ISO YYYY-MM-DD, в PostgreSQL DATE (Prisma DateTime @db.Date), без времени и timezone. Возраст вычисляется при необходимости по календарной дате и согласованной зоне; не хранить второй изменяемый возраст. Сервер отклоняет отсутствующую, невозможную, будущую и не соответствующую формату дату. Минимальный допустимый возраст, допустимый нижний предел даты, изменение после регистрации и правило расчёта возраста для 29 февраля согласовать отдельно. Не открывать production до принятия необходимых бизнес-ограничений.

Greenfield: не сохранять прежнее числовое поле, nullable дату или legacy parser. Чистая БД из unreleased миграций, обязательная дата в каждой записи профиля. Не открывать бизнес-кабинет с незавершёнными обязательными полями. Дату рождения не включать в публичный поиск по username, ответы availability, логи или общие карточки сотрудников без отдельного основания и прав.

UI: общий переиспользуемый компонент на существующей shadcn/ui системе; текстовое поле и доступный календарь с общей канонической датой. Валидный полный ручной ввод обновляет выбранную дату и месяц/год календаря, выбор календарём обновляет текст; неполный/некорректный ввод сохраняется для исправления, не подменяется последним валидным значением при отправке. Предлагаемый формат RU ДД.ММ.ГГГГ, EN согласно явно указанной локали; быстрый выбор месяца/года, видимый focus, клавиатура, Escape, возврат фокуса, touch, обе темы. Реальные зависимости picker проверить и согласовать до добавления.

Приёмка: все роли, email/Telegram, пустая дата, 31 апреля, 29 февраля в високосном/невисокосном году, будущее, формат, ручной ввод → календарь и обратно, смена года/месяца, исправление ошибки, сохранение после возврата шага/сетевого отказа, восстановление draft после verification, старый профиль без даты, права и отсутствие утечек, RU/EN dark/light desktop/mobile. Это проектирование; код, миграция и UI даты рождения пока не реализованы.

## Срез 6.1 — дата рождения, greenfield

По решению владельца от 27.11.2026 удалены числовое поле возраста и ветки совместимости. В исходной unreleased auth migration теперь birth_date DATE NOT NULL с CHECK по UTC-дате создания, company_name по роли, отдельные промежуточные миграции профиля удалены. Prisma DateTime @db.Date. Один строгий profileInput для черновика и защищённого POST /profile, обязательны дата и название компании для владельца; GET /profile возвращает ISO дату. Неподтверждённый пользователь по-прежнему не получает сессию или профиль. Данные не раскрываются в session/username API. Старый числовой инпут удалён: текущая форма завершения регистрации использует общий Input type=date с календарём браузера и обязательным полем для всех ролей, RU/EN, ошибки и сохранение ввода. Полный собственный picker с ручным форматированным вводом и двусторонней синхронизацией, а также новый wizard ещё открыты; текущий signup/onboarding действуют до замены, не как legacy API после выпуска. Тесты проверяют новую обязательность, невозможные даты, CHECK/NOT NULL, все роли, реальную email-регистрацию и UI. 18+ не добавлено. До первого релиза старые тестовые БД с другими checksum пересоздавать только при подтверждённой одноразовости; main и реальные БД не менялись. Не отключать production gate.

## Срез 6.2 — общий DatePicker

В UI добавлены общие Calendar, Popover и DatePicker на основе shadcn new-york-v4, DayPicker 9.14.0, Radix Popover 1.1.15 и date-fns 4.1.0 (владелец согласовал 27.11.2026). Контролируемый текст хранится в форме; строгое преобразование в ISO выполняется при отправке, невалидный/неполный ввод не подменяется прежней датой. RU ДД.ММ.ГГГГ, EN MM/DD/YYYY, ISO допускается для вставки и autofill. При открытии календарь отображает месяц валидной даты, выбор возвращает локализованный текст, месяц и год доступны в dropdown; ограничения min/max и UTC согласованы с сервером. Пока сохраняется отсутствие минимального возрастного ограничения. Storybook, unit и E2E обновлены; форматирование, lockfile, реальные тесты и ручная приёмка ожидаются. Не считать quality пройденным, не менять frozen install, production gate и main.
