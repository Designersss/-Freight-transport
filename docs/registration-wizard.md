# RD-04 — пошаговая регистрация MOVARO

Статус: требования владельца от 27.11.2026, технический сценарий предложен для согласования. Связано с #5 и PR #24. Текущая одноэкранная форма профиля подлежит замене, не является финальной визуальной приёмкой.

## Пользовательский сценарий

1. Учётные данные: email, пароль; проверка формата и согласованной длины. Имя переносится на шаг профиля. Продолжить.
2. Выбор роли: три самостоятельные карточки «Владелец компании», «Диспетчер», «Водитель». Активация карточки мышью, touch или клавиатурой немедленно переводит на следующий шаг; отдельной кнопки продолжения нет. Роль до финального сохранения можно изменить через «Назад». PLATFORM_ADMIN отсутствует.
3. Профиль: имя и фамилия обязательны для всех. Владелец указывает название компании. Водитель и диспетчер могут указать возраст и выбрать фото. Возраст и фото необязательны, как в прежних решениях для водителя; необязательность возраста диспетчера — предложенная интерпретация нового требования. Фото можно удалить/заменить до сохранения. Кнопка завершения регистрации.
4. Подтверждение почты по ссылке остаётся обязательным. Предлагаем отправлять письмо после завершения формы, сохранять данные регистрации на сервере и после подтверждения/входа восстанавливать профиль без повторного ввода. При неподтверждённой почте вход запрещён и открывается экран подтверждения. Не выдавать сессию до проверки email. Если пользователь уже зарегистрирован, но не закончил профиль, при входе продолжить с недостающего шага.

## Визуальный контракт

Сохранить существующий AuthPanel, Manrope, семантические токены, компактную типографику, dark/light, RU/EN. Шаги имеют понятные заголовки и индикатор фактического прогресса; «Назад» возвращает предыдущий шаг, сохраняя ввод в рамках текущей формы. Карточка роли — доступная кнопка с иконкой, названием, коротким описанием и стрелкой; без предвыбора, без второй кнопки. Переходы CSS opacity/transform, ориентир 180–220 мс, без задержки действий и с отключением необязательного движения при prefers-reduced-motion. Фокус на заголовке следующего шага, Tab/Enter/Space, видимый фокус. Без новых библиотек, без изменения общих токенов. Точные отступы/время анимации — предложенные, проверить в браузере.

## Технические границы и вопросы

- Текущий signup требует name; текущий profile endpoint разрешён только подтверждённой сессии, возраст хранится в driver_age с ограничением DRIVER. Не переносить выдачу роли в клиент и не разрешать создание активного профиля без подтверждения. Нужно согласовать и реализовать серверный черновик регистрации, связанный с конкретным account id, или эквивалентный атомарный механизм Better Auth. Проверить повторы signup, конкурентные запросы, отсутствие сессии, запрет admin, ошибку SMTP и восстановление незавершённого сценария. Не хранить пароль в localStorage/sessionStorage/URL; Better Auth выполняет хеширование.
- Название компании — новое требование RD-04 к сбору данных, ранее данные компании относились к RD-05. Предлагается хранить название как данные незавершённого создания компании; не создавать фиктивное членство или готовую компанию до реализации домена RD-05. Полный процесс компании остаётся RD-05.
- Миграция возраста должна сохранить существующие значения driver_age и обеспечить допустимость возраста для DRIVER/DISPATCHER, не для других ролей. Пределы возраста согласуются отдельно; не вводить бизнес-ограничение без основания.
- photoKey уже есть, но API загрузки профиля ещё нет. Реализовать действительную приватную загрузку JPEG/PNG с проверкой содержимого, лимитом размера, полномочиями, очисткой брошенных файлов и безопасным чтением. При выборе фото до подтверждения требуется защищённая ограниченная временная загрузка, привязанная к регистрации, без выдачи рабочей сессии; альтернатива — подтверждение email перед выбором роли и загрузка только после входа. До проверки этой границы не выдавать сохранение фото за реализованное. Не хранить произвольный URL/photoKey из клиента.
- Действующий API с одноразовым выбором роли и серверными гарантиями сохранить или мигрировать с обратной совместимостью. Не открывать production gate. Telegram следует тому же сценарию профиля, без повторного создания аккаунта.

## Приёмка

Реальный браузерный сценарий email → role → role-specific profile → verification → login → восстановление сохранённого профиля. Все три роли, возврат назад, повтор/ошибка отправки, перезагрузка/новый браузер после регистрации, запрет смены роли и администратора, отказ неподтверждённой сессии, безопасная загрузка и удаление фото. RU/EN × dark/light × desktop/mobile, клавиатура и reduced motion; axe/overflow, реальный PostgreSQL и SMTP, реальные storage integration tests. Не использовать production-заглушки. Существующий обязательный quality CI и ручная приёмка владельца.

## Порядок реализации

1. Устранить текущий CI blocker PR #24; не считать существующий одноэкранный UI принятым.
2. Согласовать точный момент подтверждения почты и схему хранения незавершённой регистрации, расширить контракты/миграции и права, реализовать загрузку.
3. Собрать многошаговый интерфейс с анимациями, интегрировать с реальным API.
4. Переписать затронутые E2E по новому сценарию без ослабления прежних инвариантов; ручная визуальная приёмка, затем разрешение на merge.

Источники проекта: #5, DESIGN.md, docs/architecture.md, schema.prisma, packages/auth/src/contracts.ts, packages/auth/src/profile.ts, packages/storage/src/file-policy.ts. Конкретный механизм Better Auth draft/upload пока не выбран, требует проверки официального API закреплённой версии.

## Мобильная версия и PWA

Дополнение владельца от 27.11.2026: проектировать каждый шаг для смартфона и установленного приложения с тем же вниманием к компоновке, движению и удобству touch, что и desktop. Проверить безопасные зоны, экранную клавиатуру, видимость полей и кнопок, возврат между шагами, выбор фото с телефона и запуск ссылки подтверждения из почтового приложения. Переходы не задерживают действия; reduced motion сохраняет функциональность. Не предполагать общую сессию браузера и установленного PWA. См. [Mobile & PWA](mobile-pwa.md). Техническая реализация и приёмка ещё открыты.

## Срез 1 — совместимое расширение профиля

Новая additive Prisma/SQL миграция 20261127050000_registration_profile_fields добавляет nullable company_name, расширяет CHECK driver_age на DRIVER и DISPATCHER, запрещает company_name у иных ролей, пустые и длиннее 200 символов названия. Существующие данные и роль не изменяются. В API сохранено техническое имя driverAge для совместимости; это возраст водителя или диспетчера. GET/POST /profile возвращает companyName (null у старых профилей), разрешает ввод только владельцу. Для будущего wizard отдельная registrationProfileInput требует название компании у владельца, legacy профиль может быть без него. Компания/членство не создаются. Длина названия до 200 — предложенный технический предел, возраст положительный PostgreSQL integer, без новой бизнес-границы. Проверки схемы расширены на реальные ограничения, HTTP-тест на запрещённые поля и конкурентный выбор с возрастом диспетчера, существующий browser E2E на новый DTO. Новые поля пока не подключены к старому UI. Новая регистрация до подтверждения, черновик, фото и анимации ещё не реализованы. Предыдущие миграции не редактировались; fresh migration и тесты должны пройти CI, upgrade с заполненными данными проверяется отдельно до production.

Для следующего среза рассмотрен Better Auth 1.7.28 additionalFields: signup валидирует и сохраняет дополнительные поля при создании пользователя, существующий email получает synthetic response без обновления, письмо отправляется после транзакции. Предлагается хранить только валидированный черновик без пароля и секретов на записи пользователя, не отдавать его в публичных ответах и материализовать профиль атомарно после подтверждённого входа. Механизм ещё не реализован; проверить обработку ошибок, конкурентность, повторный signup и привязку к реальному user id. Источник: https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/api/routes/sign-up.ts .
