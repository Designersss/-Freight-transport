# ADR: Telegram-авторизация через собственного бота (RD-04)

Статус: продуктовый сценарий утверждён владельцем 28.11.2026; техническая реализация и проверки открыты. Задача #5, Draft PR #24. Новый сценарий заменяет прежний OIDC, описанный в исторических срезах auth-rd04.md. До завершения замены не считать Telegram готовым к приёмке.

## Контекст и решение

На защищённом HTTPS staging 28.11.2026 Telegram подтвердил вход, но MOVARO вернул /ru/login?telegram=error. Первопричина callback не установлена. Владелец выбрал собственный бот вместо окна OAuth независимо от этого дефекта. Использовать один бот, grammY, long polling, отдельный apps/bot и постоянный Docker-контейнер, без публичного webhook. Backend остаётся владельцем данных и решений, Better Auth — владельцем сессий; bot не получает доступ к бизнес-таблицам и не выдаёт браузерные сессии.

## Утверждённый пользовательский контракт

- Вход, регистрация и первоначальная привязка Telegram используют единый механизм с разными intent. Telegram не нужен в Admin.
- Web создаёт запрос и открывает deep link в бота; остаётся экран ожидания с кнопкой повторного открытия Telegram, отменой, истечением и повтором. Telegram-клиент может требовать явного нажатия Start; не отправлять сообщение от имени пользователя принудительно.
- Бот в личном чате показывает действие, подтверждение и отклонение, предупреждает не подтверждать чужие запросы. RU/EN; язык запроса сохраняется.
- При новой регистрации обязательна отправка своего контакта через request_contact. Чужой, пересланный, введённый текстом контакт или контакт без совпадающего user_id не подтверждает номер. Это доказательство получения собственного контакта от Telegram, не независимая SMS-проверка. При повторном входе номер не запрашивать.
- После подтверждения Web автоматически продолжает сценарий в исходном браузере. Ручной ввод кодов не требуется. При регистрации имя и фамилия предзаполняются при наличии и редактируются; роль, дата рождения, компания по действующим правилам и уникальный username обязательны. Фото из Telegram не импортировать; прежнее правило фото после подтверждения реального email сохраняется.
- Login неизвестного Telegram не создаёт аккаунт. Register существующего Telegram не создаёт дубликат; явно направить к входу. Привязка требует свежей действующей email-сессии, сохраняет user id, не объединяет аккаунты по имени, номеру, username или email. Отвязка/замена запрещена.
- Запрос действителен 5 минут, новый запрос в том же браузерном контексте отменяет прежний. Отмена и истечение не создают аккаунт, связь или сессию.

## Технический проект и инварианты (проверить до активации)

- API создаёт случайный 32-байтовый одноразовый deep-link capability (base64url 43 символа, лимит Telegram 64), отдельный случайный browser capability в host-only HttpOnly Secure cookie. В PostgreSQL хранить хеши секретов, срок, intent, locale, статус, минимальную идентичность, при link — user/session/revision. Не помещать browser capability, пароль или session token в deep link. Не логировать capabilities, номер, содержимое update или cookies.
- Разделить claim (привязка запроса к Telegram user/chat), сбор собственного контакта для register, явное approve/reject и consume в исходном браузере. Предлагаемые состояния: pending, claimed, approved, rejected, cancelled, expired, consumed. Все изменения атомарны и проверяют expiry по серверным часам; терминальные состояния не возобновляются. Дубликаты update и concurrent approve/consume безопасны. Новый start не заменяет уже заявленного Telegram пользователя.
- Browser status не раскрывает чужую идентичность, а finish требует browser capability и проверку Origin. Бот аутентифицируется отдельным scoped service secret на приватном API, не посредством публичного Web proxy. Проверять private chat, from.id, chat id, contact.user_id и принадлежность callback конкретному запросу. Не использовать username/phone как идентификатор. Telegram numeric user id хранить без потери точности; OIDC sub не считать тем же ID.
- Deep link является передаваемым секретом, поэтому одной кнопки approve недостаточно для защиты от login CSRF/social engineering. Предлагаемое усиление: явное сопоставление короткой случайной метки на сайте и в боте без ввода кода, объяснение цели и предупреждение о чужих ссылках; проверить отказ при неверном контексте, пересылке и гонках. При невозможности надёжно закрыть риск согласовать дополнительный шаг привязки устройства до активации.
- Для финализации использовать поддерживаемую точной версией Better Auth 1.7.28 серверную интеграцию. Отдельный compatibility spike обязан подтвердить создание/чтение/отзыв штатной сессии, session hooks, public/admin isolation, Secure cookie и transactional replay semantics на PostgreSQL. Не выдавать самодельный session token, не создавать второй session manager, не обходить проверку доступа. Не считать схему сессии утверждённой до spike.
- Номер хранить только для завершённой регистрации с доступом владельца и ограниченных серверных операций; определить точную модель, нормализацию, retention незавершённых запросов и правила отображения до миграции. Не вводить уникальность номера или вход по телефону без отдельного требования. Не показывать internal email .invalid, не считать его подтверждённым. Удалять временные персональные поля после истечения/consume. Существующие профильные проверки и запрет admin сохраняются.
- Rate limits по browser/IP, Telegram user и глобальный предел; bounded polling/backoff, дедупликация, безопасные ошибки, проверка недоступности Telegram и перезапуска бота. Один экземпляр polling на токен, graceful shutdown, readiness отдельно от процесса. Не передавать Bot API token в Web/Admin или Git/build.

## Этапы замены и gates

1. Инвентаризировать OIDC-потребителей, fixtures, env, OpenAPI/Orval, схемы/SQL predicates, readiness и документацию; закрыть старый flow на staging до переключения.
2. Compatibility spike на Better Auth и PostgreSQL. Затем модель запроса, атомарные операции и тесты конкурентности/истечения/чужих идентификаторов. Согласовать точный контракт приватного bot API.
3. Реализовать apps/bot, закрепить согласованные зависимости и лицензии, private API adapter, контакт/подтверждение/отмена, RU/EN и восстановление после рестарта.
4. Web: login/register/link, состояния ожидания, отмены и истечения, корректное возвращение из Telegram, PWA/mobile, клавиатура и обе темы. Существующий onboarding, email и Admin не ломать.
5. Удалить заменённые OIDC endpoints, provider, callback, credentials, тесты протокола и тексты из действующей реализации; обновить API генерацией, а не ручной правкой generated. Сохранить регрессионные утверждения о безопасности и ролях. Исторический Git не переписывать.
6. Миграция только проверенным способом после инвентаризации staging. Уже применённые миграции не переписывать, реальные/непроверенные данные не очищать. Если выявлены OIDC-only записи, не отождествлять их с Bot API ID; отдельно согласовать тестовую очистку или безопасную повторную привязку. Сохранять администратора, email-аккаунты и volumes.
7. Deploy закрытого staging, backup/restore, отдельный bot token, реальная регистрация/вход/link, отмена и повтор. Проверить password reset HTTPS отдельно. Полный quality на актуальном head, ручная приёмка и явное разрешение на merge.

## Compatibility spike: выдача штатной сессии

В изолированный Testcontainers suite добавлен telegram-bot-session.test.mjs. Test-only plugin использует createAuthEndpoint, internalAdapter.consumeVerificationValue, createSession и setSessionCookie из той же установленной Better Auth 1.7.28, что и действующие hooks MOVARO. Синтетический grant моделирует уже подтверждённый браузерный запрос; не выдаётся публичным API. Старый OIDC plugin в этой фикстуре заменён, действующие session hooks, ограничения PostgreSQL, secure cookie и Admin остаются. Проверки: неверный browser proof и Origin, параллельный consume двумя экземплярами Better Auth, ровно одна сессия с telegramAccountId, отсутствие adminSession, подписанная host-only Secure/HttpOnly/SameSite=Lax cookie, изоляция Admin (включая переименование cookie), повтор, logout, expiry, отсутствие связи и деактивация. Fixture не отправляет почту и не обращается к Telegram.

Источники закреплённой версии: https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/plugins/magic-link/index.ts ; https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/db/internal-adapter.ts ; https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/src/cookies/index.ts ; https://github.com/better-auth/better-auth/blob/v1.7.28/packages/better-auth/package.json .

Ограничение: consume и createSession в spike не объединены в общую транзакцию; при отказе после consume grant теряется, повтор запрещён. Это проверка at-most-once и совместимости сессии, не доказательство атомарности регистрации/привязки/consume. Для production design отдельно проверить транзакционную границу и отказ после consume, не ослаблять hooks. Реальный бот, модель запросов, browser handoff и link пока не реализованы. До фактического прогона spike gate открыт.

## Второй срез: действия Telegram

Добавлены внутренние claim/contact/decide и bounded deleteExpiredTelegramBotRequests без открытия маршрутов. Claim допускает первое присвоение или повтор того же private actor, не заменяет владельца, имена записывает только при register и первом claim. Contact требует совпадения private chat/from/contact.user_id, forwarded=false, нормализует только международные цифры с необязательным начальным плюсом и не позволяет перезаписывать уже принятый номер другим. Bot adapter ещё должен доказать происхождение update, отсутствие forwarding, связь с конкретным актуальным prompt (не принимать произвольную карточку контакта в контексте старого запроса); совпадение ID не означает независимую проверку SIM. Решение атомарно ограничено claimed, идентичностью и expiry; register approve требует контакт, login не требует, reject стирает временные персональные данные. Approval не создаёт сессию или аккаунт. Cleanup удаляет до 500 истёкших строк по expiry с FOR UPDATE SKIP LOCKED; worker scheduling и гарантии retention при сбое пока открыты. После очистки browser status возвращает отсутствие запроса, UI должен трактовать это как истечение/недействительность. Остаточный риск пересылки deep link не закрыт одной визуальной меткой; необходим отдельный security review до включения.

Расширен существующий PostgreSQL integration test: race claim и approve, private chat, foreign/missing/forwarded contact, phone normalization, запрет изменения принятого номера, повтор claim, login без телефона, reject scrub, expiry/cleanup. Исправлены два форматирования из Quick Checks 46141838694 (сборка 5/5 и OpenAPI/Orval прошли, lint failed, typecheck skipped). Новые тесты не запускались. Источники: https://core.telegram.org/bots/api#contact ; https://core.telegram.org/bots/api#keyboardbutton ; https://www.postgresql.org/docs/17/sql-update.html ; https://www.postgresql.org/docs/17/sql-select.html .

## Транзакционная финализация привязки

Quick Checks 46142047298 на df28c2b205fd0e195f7550228c57f55c8d5221c6 завершились успешно. Новый внутренний finishTelegramBotLink блокирует владельца, затем подтверждённый запрос, проверяет browser hash, intent, user/session snapshot, revision, активную публичную роль, проверенный email, свежесть credential session, отсутствие Telegram-связи и повторно использует существующий SQL binding guard. INSERT account, increment revision существующим trigger и consume со стиранием временных полей выполняются в одной транзакции. Отмена, expiry, replay, revoked/stale session и unique conflict не выдают новую сессию и не создают связь; при конфликте транзакция откатывается. Для Bot API выбран префикс bot: в accountId, providerId telegram сохраняет existing permanent binding/unique constraints. Это техническое решение, не миграция старых OIDC subjects: перед активацией требуется проверка отсутствия конфликтующих исторических accountId, отключение OIDC и отдельный review схемы идентичности. Номер для link не запрашивается. API boundary пока не подключён, identity должна поступать только из подписанной сессии. Login/session issuance и registration finalization остаются отдельными задачами. Добавлен PostgreSQL integration test concurrent consume, wrong browser/owner/session, duplicate account rollback, revoked/stale session, cancel; фактический запуск ещё не выполнен. Источники: https://www.postgresql.org/docs/17/trigger-definition.html ; https://www.postgresql.org/docs/17/transaction-iso.html .

## Вход: атомарный consume в Better Auth

Добавлен выключенный до подключения API plugin createTelegramBotLoginPlugin. Origin, независимая host-only cookie, requestId, существующая активная публичная identity из bot: namespace; отказ при уже существующей сессии. Не создаёт пользователя. Штатный internalAdapter.createSession получает proof только через server-only AsyncLocalStorage/hook; setSessionCookie остаётся единственным способом выдачи подписанной cookie. Migration 20261128090000_telegram_bot_session_fence добавляет два ephemeral поля с CHECK NULL и trigger session_guard_bot_login. Trigger после owner-lock существующего session_guard_account_status проверяет bot account, активный полный публичный профиль и browser grant, погашает его в том же INSERT; откат INSERT восстанавливает grant. Для bot: account нельзя вставить Telegram session без proof. Старые OIDC fixture sessions и email sessions не требуют bot proof. Никаких изменений применённых миграций. Readiness manifest обновлён. Cookie пока только читается в отдельном тестовом plugin, выдача cookie и HTTP allowlist/rate limits предстоят; не подключать plugin к deployed runtime до устранения relay/login-CSRF риска. Недоставка HTTP ответа после успешной вставки не откатывает сессию; повтор требует нового запроса.

Integration: реальный plugin в Better Auth instance, wrong browser/origin, rollback при NOT NULL failure, race двух instances, signed cookie, consumed proof fields, replay и деактивация. Непроверенные варианты: linked email login, missing/expired/cancelled request, existing cookie, admin separation на новом plugin, error mapping driver и race, полная регрессия. Предыдущий Quick Checks 46142245494: build/API generation success, lint failed на одном форматировании теста привязки; исправлено. New tests not executed locally.
