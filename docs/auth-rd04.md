# RD-04 — авторизация и границы доступа MOVARO

Задача #5, родитель #1. Основание: решения владельца 26.11.2026 и принятый RD-03 (#22). Это проектирование первого среза, не реализованный runtime.

## Подтверждённые требования

- Четыре взаимоисключающие роли: PLATFORM_ADMIN, COMPANY_OWNER, DISPATCHER, DRIVER (технические имена предлагаются здесь). Публичная регистрация только для последних трёх; роль после назначения не редактируется самим пользователем.
- Имя и фамилия обязательны. Полная дата рождения обязательна для всех публичных ролей; фото необязательно. Данные компании, категории и назначения техники — последующие этапы.
- Email/пароль и Telegram; для Telegram не требовать email/пароль. Привязка только после доказанного владения обоими аккаунтами. Не связывать по совпадению имени, username или непроверенной почты. Глобальный администратор — отдельный Web Admin, без публичной регистрации и Telegram-входа.
- Подтверждение реального email ссылкой, сброс пароля одноразовой ссылкой на 15 минут, список сессий и отзыв. Деактивация с проверкой активных операций и необходимой историей; не обещать физическое удаление без отдельной политики хранения и юридического review.
- Первый PLATFORM_ADMIN создаётся защищённой серверной командой, без секретов в CLI arguments, Git и логах.
- Реальные формы RU/EN, dark/light, общая UI-библиотека. Принимаются в браузере.

## Предлагаемая архитектура

Единственный runtime авторизации — NestJS API (Better Auth как библиотека, без параллельного Next auth backend). Общие контракты и схемы в packages/auth или contracts по реальной необходимости; Next web/admin потребляют API. Серверный guard получает сессию из cookie, проверяет состояние пользователя и серверную роль; UI не является границей безопасности. Точные origin, host-only HttpOnly cookies, Secure в HTTPS, CSRF/origin validation. Никакого хранения session token в localStorage. Топология reverse proxy и cookie isolation Web/Admin требуют отдельной проверки перед включением маршрутов. Не открывать production Admin до проверки guards и негативных тестов.

Применяем Better Auth 1.7.28, уже проверенный в RD-02 изолированным PostgreSQL/Testcontainers и Fastify adapter (не production runtime). Сначала сверить схему и API точной версии; миграции управляются Prisma, не автоматически при старте приложения. Не дублировать хранение паролей/сессий в собственных таблицах.

Логические сущности (не физическая схема):

- User — устойчивый ID, имя, фамилия, роль, статус, timestamps; данные идентификации и сессии принадлежат Better Auth. Не возвращать внутренние поля/секреты через публичный API.
- Account — уникальность идентичности по provider + provider account ID; credential и Telegram принадлежат одному User при подтверждённой привязке.
- Session — серверные сессии, отзыв и проверка деактивации. Не полагаться на устаревший cookie cache для авторизации.
- Verification — токены подтверждения/сброса по поддерживаемой схеме Better Auth, не логировать, проверять срок/одноразовость.
- DriverProfile — дополнительные необязательные данные водителя. Дата рождения обязательна в общем профиле. Фото — через private storage после проверки прав и типа файла.

Назначение роли и профиль не должны принимать произвольные поля от клиента. Данные и права проверять сервером; уникальные ограничения и конкурентные тесты на дублирующую регистрацию/привязку. Никакого доступа к бизнес-операциям до завершения onboarding. Отдельно проверять запрет входа/отзыва активных сессий деактивированного аккаунта.

## Критические вопросы реализации

1. Better Auth 1.7.28 требует строковое поле email в core user schema, а email sign-up проверяет формат. Telegram-only регистрация не должна требовать email согласно утверждённому ТЗ. До выбора физической схемы выполнить compatibility spike на точной версии: поддерживаемый способ идентификации без настоящего email, изоляция от email login/reset/verification и implicit linking, исключение коллизий. Не создавать вымышленные реальные email, не отмечать непроверенную почту verified, не менять ядро Better Auth вручную. Если поддерживаемый вариант отсутствует, вынести альтернативу на согласование до реализации Telegram. Не объявлять сценарий готовым.
2. Email delivery: реальный транспорт, в dev/test локальный почтовый приёмник и настоящие письма; production требует настроенный SMTP/провайдер и безопасную конфигурацию. Не делать no-op sendVerificationEmail и не выводить токены в логи. Проверить доставку, срок, повторное использование, отсутствие enumeration и rate limits.
3. Telegram: официальный механизм входа, проверка подписи/issuer/audience/nonce/state и replay защиты по выбранному протоколу. Не использовать username как ID; не доверять полям клиента. Точный протокол и поддерживаемая интеграция проверяются отдельно до кода.
4. Деактивация и активные операции: до появления бизнес-модулей не имитировать успешную проверку активных заявок. Определить контракт policy и не открывать неполноценную операцию в production. Отдельно политика хранения/удаления персональных данных.

## Физическая модель — первый migration срез

Prisma управляет стандартными таблицами Better Auth 1.7.28 (user/account/session/verification и rateLimit для дальнейшего database-backed rate limiting), сохраняя физические camelCase поля для ранее проверенного pg adapter. ID Better Auth — TEXT, время — TIMESTAMPTZ(6); никаких runtime schema migrations. Добавлены уникальность provider+account, email, session token и rate limit key, внешние ключи, индексы и ограничения нормализации/неподтверждённого внутреннего email @telegram.invalid.

Профиль MOVARO — отдельная таблица user_profiles, один User → максимум один профиль с обязательной ролью и именем/фамилией. Отсутствие профиля означает незавершённый onboarding; будущие guards должны отказать в бизнес-доступе. Дата рождения обязательна, DATE без времени, фото необязательно. Отдельный DriverProfile не создаём без необходимости. Фото — ключ приватного объекта, загрузка пока не реализована. Статус ACTIVE/DEACTIVATED, FK RESTRICT не даёт случайно удалить пользователя с профилем. Смена роли, выдача admin, проверка деактивации и email namespace на HTTP остаются будущими server policies, не гарантия одной миграции. Не добавляем FK к существующим user_event_streams до реализации миграции бизнес-получателей и проверки прежних тестов.

Testcontainers больше не запускает Better Auth runtime migrations: read-only план getMigrations должен не требовать создания таблиц, колонок и индексов. Добавлен тест реальной Prisma модели и SQL constraints, включая конкурентную уникальность provider account, обязательную дату рождения и FK. ## Ручная приёмка 26.11.2026 — замечания владельца

Пароль 6–128 по требованию владельца (ранее 12–128); единые константы и Zod в обеих частях, maxLength, no request при невалидных данных. 6 — слабый минимум для однофакторной авторизации, production activation остаётся запрещена, необходимо отдельное согласование политики безопасности (более длинный пароль или MFA). EMAIL_NOT_VERIFIED передаётся только после проверки пароля Better Auth; вход без подтверждения невозможен. Убрана отдельная ссылка на подтверждение из login, повторная отправка на соответствующем экране, подтверждение по ссылке ведёт на login, не создавая session. Ошибка неправильных credentials нейтральна, поля очищаются после попытки HTTP независимо от исхода, локальная ошибка сохраняет ввод. Один тонкий border фокуса. SMTP local Mailpit только ловит сообщения, не отправляет в публичные почтовые сервисы; добавлен диагностический код AUTH_SMTP_DELIVERY_FAILED без PII и токенов. Signup в Better Auth обрабатывает отправку после транзакции; успешная регистрация не гарантирует доставку, повторная отправка предусмотрена.

Anti-abuse: сохранён Better Auth database-backed IP/path limiter, добавлен атомарный лимит запросов почты в PostgreSQL независимо от наличия пользователя: verification (signup/resend) и reset отдельно, 1/60с и 5/час на нормализованный HMAC email, общий бюджет 60/мин и 1000/сутки, ответ 429 Retry-After. Значения выбраны как стартовые, не окончательные production quotas. Учитываются валидные запросы, а не только отправленные письма, возможен отказ легитимному пользователю при атаке на его email или исчерпании общего бюджета; нужны мониторинг, edge rate limiting, доверенная IP topology и дополнительная защита до production. Транзакция бронирования не держится при SMTP. Добавлена пятая миграция, негативные и конкурентные проверки. Не подтверждены запуск и доставка в локальном окружении владельца.

## RD-04 — серверный выбор роли (dev/test)

Используем существующие user_profiles, PK user_id, enum ролей и CHECK имени/даты рождения. Без новой миграции. Роль назначается один раз через INSERT ON CONFLICT (user_id) DO NOTHING; при двух параллельных запросах только один создаёт профиль. Никакого UPDATE роли через публичный API.

GET /api/v1/auth/profile возвращает null для незавершённого onboarding либо DTO firstName, lastName, role, birthDate, companyName. POST /api/v1/auth/profile принимает строго firstName, lastName, role (COMPANY_OWNER, DISPATCHER, DRIVER), обязательную ISO дату рождения и обязательное companyName только для владельца. Ограничение имён 200 символов соответствует текущему auth contract; возрастное ограничение не согласовано. Субъект берётся из серверной Better Auth session, не из тела запроса. Для POST требуется точный Web Origin. Ответ 201 при создании, 409 при повторе/конкуренции, 401 без сессии, 403 для неподтверждённой почты, деактивированного профиля или PLATFORM_ADMIN, 400 для невалидного DTO/query. Никаких токенов, внутренних статусов или photoKey в DTO; no-store.

Это первый срез профильного API в существующем явном Fastify auth adapter, пока вне Nest OpenAPI (как другие auth routes); OpenAPI-контракт и генерацию клиента для бизнес-модулей не изменяем. Web proxy и экран выбора роли, guards на рабочие маршруты, запрет входа деактивированных пользователей, защищённый bootstrap admin и Telegram остаются открытыми. Production auth по-прежнему запрещён. Тест расширяет существующий реальный email HTTP flow: неподтверждённый/отсутствующий сеанс, запрет admin/чужих полей, конкурентный выбор и повтор, деактивированный профиль, отозванная сессия. Не выдавать проверку профильного endpoint за полную RBAC или деактивацию.

## Запрет публичного входа для деактивированных аккаунтов и администраторов

В runtime публичной email-авторизации проверяем состояние профиля перед созданием сессии через Better Auth databaseHooks.session.create.before и повторно при выдаче get-session. Деактивированный профиль и PLATFORM_ADMIN не получают новую публичную сессию; ответ входа общий INVALID_CREDENTIALS, без cookie. Существующая cookie не позволяет получить публичный DTO сессии при запрещённом статусе. Для первого подтверждённого входа без профиля сохраняется создание профиля из registrationDraft. Это не реализация команды деактивации, отзыва всех сессий или отдельной авторизации Admin; эти границы и конкурентные сценарии остаются открытыми. Интеграционный тест проверяет отказ входа, отсутствие новой записи сессии и cookie, запрет get-session и profile при смене состояния. ## Telegram — срез 14.1: проверяемый OIDC-адаптер

Выбран официальный Telegram OpenID Connect Authorization Code + PKCE, а не legacy iframe/widget hash. Telegram не предоставляет UserInfo endpoint; используем ID token. Better Auth 1.7.28 genericOAuth requireIdTokenVerification требует discovery issuer/JWKS и проверяет подпись, audience, required claims и сохранённый nonce до getUserInfo. createTelegramProvider использует фиксированный discovery/authorization/token на oauth.telegram.org, client_secret_basic, openid/profile, без phone и bot_access, без override профиля и logout внешнего аккаунта. getUserInfo только проецирует уже проверенный ID token, дополнительно требует точный issuer/audience/sub/nonce; отсутствующий или некорректный JWT отклоняет. Никакой собственной криптографии проверки JWT. Identity — непрозрачный OIDC sub, не username, имя или numeric id. Внутренний sha256(sub)@telegram.invalid остаётся emailVerified=false; внешние email/email_verified/picture игнорируются. Для работы с Bot API отдельное подтверждённое соответствие numeric Telegram id ещё предстоит, sub с ним не отождествляем. Отдельный partial UNIQUE запрещает более одного Telegram account на User; существующий UNIQUE(providerId, accountId) предотвращает передачу одного subject двум User. Индекс SQL-only, Prisma schema не описывает partial index.

Адаптер пока НЕ зарегистрирован в публичном runtime. Изолированный тест использует тот же provider config и настоящее ядро Better Auth/PG, локальный discovery/JWKS и подписанные RS256 fixture tokens; внешний обмен code заменён только в тесте, PKCE verifier проверяется. Проверки: unknown sign-in не создаёт пользователя, state/issuer/audience/expiry/nonce/подпись/replay отклоняются, signup только explicit, повторный вход сохраняет User, ложный email/verified/image игнорируется, второй Telegram на тот же User запрещён. Отдельно нужны explicit linking с fresh session и повторной eligibility проверкой, race/link conflict, Telegram-only onboarding и session capability (не ослаблять проверку email для email-аккаунтов, не отмечать synthetic email verified), callback allowlist/cookie bridge, rate limits, secure token retention, UI и реальные BotFather credentials/allowed HTTPS URLs. До проверки этих инвариантов не открывать routes. Никаких новых внешних зависимостей.

## Telegram — срез 14.2: внутренний onboarding и проверка доступа

Добавлен telegram-registration.ts: отдельный внутренний access resolver для Telegram-only, не используется как общий auth guard до интеграции callback. Проверяет существующую Telegram account запись, точное соответствие synthetic email хешу OIDC subject (PostgreSQL 17 built-in sha256/convert_to/encode), emailVerified=false, отсутствие credential и email registration draft, принадлежащую пользователю неистёкшую сессию. Возвращает onboarding только без профиля и username, active только с username и активной публичной ролью, иначе denied. Реальный email даже при linked Telegram не проходит этот путь и остаётся под существующим email gate. Внутренние идентификаторы сессии поступают только из проверенной cookie Better Auth в будущем HTTP adapter, не из тела клиента.

completeTelegramRegistration повторно проверяет общий strict registrationInput, блокирует user/account/session, повторно читает доступ, атомарно создаёт профиль и назначает username и имя Better Auth. Повтор не меняет роль или данные; UNIQUE конфликт username откатывает профиль, допускает корректный повтор. Фото остаётся null. Для Telegram-only нет требования настоящего email/пароля, но пользователь не может обходить обязательное заполнение профиля. Testcontainers проверяет чужую/истёкшую/отозванную сессию, отсутствие Telegram связи, реальные email accounts, запрет admin/фото, конкурентное завершение, уникальность и деактивацию. Тестовые DB records не заменяют реальный OAuth callback.

Источники PostgreSQL 17: https://www.postgresql.org/docs/17/functions-binarystring.html ; https://www.postgresql.org/docs/17/explicit-locking.html . Новых зависимостей и миграций нет. Существующие публичные session hooks, email-only guards/DTO и маршруты не изменены; Telegram runtime ещё закрыт. Следующие срезы: интеграция callback с безопасной выдачей сессии, публичный DTO без synthetic email, Telegram-only onboarding HTTP/UI, явная привязка/отвязка и обновление общих guards, проверка полного flow.

## Telegram — срез 14.3: сессии, DTO и endpoint завершения профиля
