# Testing & debugging

Читать AGENTS.md, docs/e2e.md, docs/storybook.md и актуальные скрипты package.json. Использовать существующие unit/HTTP/integration тесты, Storybook, apps/e2e, Playwright и axe. Не добавлять второй тестовый стек.

- Для дефекта: воспроизвести на актуальном commit/окружении, записать expected/actual, минимизировать сценарий, проверить гипотезу по логам/trace/сети без секретов, внести минимальное исправление и регрессионный тест. Не лечить симптом таймаутами, retry или force-click.
- Для новой логики определить наблюдаемый контракт, сначала тест ключевого поведения и негативного случая, затем минимальная реализация и рефакторинг; не тестировать внутренние детали ради покрытия. Если red/green не запускались, не заявлять TDD выполненным.
- Unit — чистые преобразования/валидация; integration/API — реальные права, данные, транзакции, конкурентность; E2E — ключевые пользовательские маршруты. Моки только в тестах для контролируемых границ; не подменять проверку реального сервера моками.
- Storybook: normal, pending, empty, error, disabled, overflow и длинные строки по применимости. Проверить пропущенные фото, длинные имена, большие суммы, ноль/отсутствие значения, большое число строк, сетевой отказ, двойную отправку; для календаря — пересечения, часовые пояса, конфликт резервов. Данные синтетические и изолированные.
- E2E: роли/семантические локаторы, web-first assertions, предсказуемые fixtures и cleanup; избегать фиксированных sleep, зависимости от порядка тестов, произвольных селекторов и ослабления asserts. Проверить dark/light × RU/EN × desktop/mobile для затронутого UI; перечислить реальные комбинации.
- Визуальные baseline — только после согласованного вида; стабильные шрифты, viewport, данные, тема и окружение CI. Использовать Playwright screenshot assertions при обоснованной стабильности; не маскировать проверяемую область, не обновлять baseline для скрытия регрессии. Trace/screenshots без персональных данных и токенов.
- Проверки: frozen install, pnpm check, pnpm licenses:check, pnpm e2e:install, pnpm test:e2e; интеграционные, API-контракт и stack smoke согласно существующему quality job/области изменений. Полный quality CI запускать на контрольной точке Ready for review перед ручной приёмкой и merge, а не на каждый push Draft PR; локальные целевые тесты сохраняются. После изменений повторять Draft → Ready for review. Не выключать и не ослаблять проверки. Если стенд/браузер не доступен, явно указать какие команды не запускались.

Результат: сценарии, команды, commit SHA, окружение, результат, число тестов если известно, ссылки CI/артефактов и блокеры.

## Архитектура и скорость тестов

- Перед сокращением тестов составить карту требования → риск → наблюдаемое утверждение → уровень проверки. Удалять только доказанные дубликаты с оставшимся эквивалентным утверждением, а не целые категории по числу тестов. При изменении публичного контракта обновлять независимый ожидаемый набор в тесте; не вычислять expected из production-генератора. Проверять итоговую композицию, а не только отдельный helper.
- Unit и contract: быстрые детерминированные проверки исходников, pure functions, DTO, boundary values и HTTP mapping. Интеграции: настоящие PostgreSQL/Prisma, ограничения/транзакции/гонки, SMTP/S3/worker и авторизация. Browser UI с контролируемой сетью проверяет состояние формы, локализацию и доступность; настоящий E2E проверяет только сквозные критичные маршруты. Не переносить серверные проверки в mock-only UI.
- Для многокомпонентной платформы сохранять раздельные test suites, понятные fixtures и независимое состояние; не повторять регистрацию через браузер для каждой проверки настроек. Auth setup можно переиспользовать только в рамках выделенного тестового аккаунта/worker; проверки выдачи и отзыва сессии используют свежие независимые credentials. Не сохранять cookies, OAuth codes и токены в публичных отчётах.
- Профилировать wall-clock шагов CI, Turbo cache hits и длительность тестов до/после на сопоставимом runner и неизменном наборе обязательных утверждений. Не путать суммарные длительности параллельных задач и реальное время прогона. Учитывать стоимость runner, startup/build/install и стабильность, не только время тестов.
- Typecheck не должен без причины вызывать production build: Web/Admin уже используют next typegen и tsc; Storybook — tsc. Компилировать необходимые workspace dependencies до потребителей; Prisma generate, source/dist exports и проверку полного build сохранять. Не отключать изоляцию Vitest для ускорения без доказанной независимости.
- Playwright: существующий fullyParallel для controlled browser tests; новые workers/shards только после измерения и проверки изоляции. PostgreSQL/SMTP/S3 integration не параллелить на общем изменяемом состоянии, сначала разделить базы/порты/mailboxes/object namespaces и проверить cleanup. Не включать reuse постоянных контейнеров в CI. Конкурентный бизнес-сценарий не заменять последовательными вызовами.
- CI: независимые группы могут выполняться параллельно; обязательный status quality должен зависеть от всех групп и завершаться ошибкой при failure/cancelled/skipped любого обязательного результата. Никаких continue-on-error для обязательных тестов и обхода branch protection. Full suite только на контрольной точке, Quick Checks сохраняют frozen install, api:check, lint, strict typecheck. Изменения графа проверять на свежем runner.
- Для матрицы UI сохранять dark/light, RU/EN и desktop/mobile по принятым требованиям; оптимизация повторов бизнес-логики не заменяет проверку локализации, адаптивности, клавиатуры или axe. Не блокировать шрифты/стили/изображения в визуальных проверках.

Источники и рабочий план: [docs/testing-architecture.md](../../../docs/testing-architecture.md). Внешние навыки изучаются как рекомендации, без автоматического импорта или запуска сторонних команд.
