# Database

Сначала packages/database, текущая схема, миграции, issue, реальный PostgreSQL и Prisma из lockfile. RD-03 использует Prisma 6.19.0 и PostgreSQL 17; навыки Prisma 8 и Supabase-specific команды не переносить автоматически.

- Моделировать идентичность, связи, обязательность, уникальность и владение данными. Учитывать исторические связи и деактивацию. Для tenant-данных фильтр/ограничение companyId и права обязательны; глобальные сущности и водительская занятость имеют особые правила.
- Инварианты обеспечивать БД там, где возможно: UNIQUE, FK, CHECK для одной строки, exclusion/range constraints для интервалов. RD-07 требует tstzrange/GiST и атомарного резервирования. Не реализовывать проверку «свободно?» отдельным SELECT перед незащищённой вставкой. Если Prisma не выражает constraint, использовать проверенную SQL-миграцию, тестировать на реальном PostgreSQL.
- Транзакция включает зависимые записи и outbox, короткая, без внешнего I/O; выбрать изоляцию/блокировки по инварианту, единый порядок захвата. Retry всей транзакции ограничен и только для ожидаемых transient SQLSTATE/ошибок Prisma; не повторять без разбора constraint violations. При параллельной работе тестировать действительно независимые соединения.
- Деньги: Decimal/NUMERIC, явные валюта/единица и правила округления по ТЗ, не JS float. Ставка-снимок и история при изменении тарифов. Время: хранить instants в UTC, расчёт интервалов по timezone объекта, граничные даты/DST и смежные интервалы проверять по согласованному правилу.
- Индексы по реальным запросам, select только нужных полей, избегать N+1, bounded connection pool для api/worker, план EXPLAIN на безопасных данных. EXPLAIN ANALYZE исполняет запрос: не использовать для изменяющего production SQL без отдельного разрешения и безопасного окружения.
- Миграции — review SQL, проверить fresh DB и обновление с предыдущей схемы, ограничения/объём/locking, совместимость старого приложения. Для опасного изменения план expand/backfill/contract и резервная копия/restore, где применимо; не редактировать применённую миграцию и не использовать reset/db push в production. Применять согласованные команды db:deploy/db:status после проверки окружения.
- SQL только параметризованный; не применять unsafe raw с пользовательскими данными. Не вводить RLS Supabase вместо принятой серверной авторизации. Проверки через существующие integration/Testcontainers по мере применения.

Результат: схема/SQL diff, план миграции и восстановления, подтверждённые инварианты, негативные и конкурентные тесты, результаты запросов если измерялись.
