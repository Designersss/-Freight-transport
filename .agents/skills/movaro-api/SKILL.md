# API contracts

Прочитать существующий OpenAPI exporter, packages/client-api, контракты и обработчик ошибок до изменения. Сохранять REST /api/v1, не вводить GraphQL или новый транспорт.

- Определить ресурс/операцию, вход, выход, статус и права до реализации. GET не меняет состояние; семантика POST/PATCH/DELETE и повторного вызова документирована. Для бизнес-переходов допустим явный action, если это яснее CRUD.
- Проверять path/query/body на сервере; DTO на вход и выход с явным allowlist полей. Не сериализовать внутреннюю Prisma-модель, секреты или чужие данные. Идентификатор компании в URL/теле не доказывает доступ.
- Единый формат ошибок, реальные HTTP-статусы, безопасное сообщение и корреляция. Не добавлять произвольные envelope/коды в обход принятого контракта. Учитывать ограничения выдачи, стабильный порядок, пагинацию/фильтры и ограничение размера запроса.
- Для конкурирующих действий определить контракт конфликта (включая 409, если применимо), повторную отправку и idempotency key там, где это требуется. Ключ связан с субъектом/операцией; повтор не создаёт дубликат, а иной payload с тем же ключом обрабатывается согласно контракту.
- При изменении API обновить генерацию OpenAPI/Orval через pnpm api:generate, проверить pnpm api:check и diff generated файлов. Не редактировать сгенерированный клиент вручную. Breaking change явно согласовать и проверить web/admin/bot.
- SSE: авторизовать соединение и область подписки, проверять жизненный цикл сессии, отмену, reconnect, идентификаторы событий и обработку пропуска/дубликатов по реальному протоколу. Не использовать SSE как замену подтверждения записи в БД.

Результат: обновлённый контракт, примеры без реальных данных, негативные/контрактные тесты, совместимость потребителей.
