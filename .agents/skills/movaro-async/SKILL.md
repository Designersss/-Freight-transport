# Async processing

Использовать существующие apps/worker и packages/database outbox; pg-boss 12.39.0 в базовом RD-03, версию перепроверять. Не добавлять Redis/BullMQ или брокер без отдельного архитектурного решения.

- Бизнес-запись и outbox-event в одной транзакции. Проверить действующий relay, event_publications, уникальные event_id, атомарность publication/processed_at и гарантию фактической версии pg-boss. Не менять существующую семантику доставки без обоснования.
- Обработчик типизирован и валидирует payload; idempotency на уровне бизнес-эффекта по стабильному event/job ID. Даже если очередь заявляет exactly-once для внутренних операций, внешний email/Telegram/S3 вызов может повториться после сбоя; не обещать end-to-end exactly-once без доказательства.
- Ограниченные batch/concurrency/timeout; exponential backoff при transient ошибках, terminal/permanent error отдельно, ограничение попыток, видимость последнего сбоя и порядок ручного восстановления. Повтор не должен создавать двойные назначения/уведомления/финансовые записи.
- Сетевой I/O вне транзакции бизнес-изменения; не удерживать блокировки на ожидании внешних систем. Проверять crash между шагами, несколько worker, restart, duplicate, retry, graceful shutdown, retention и backlog. Не удалять необработанные события автоматически.
- Версионировать контракт событий при реальных несовместимых изменениях, не включать лишние персональные данные/секреты. Подписчик проверяет доверенную область и не заменяет авторизацию. SSE-инвалидация не источник истины о commit.
- Мониторить возраст необработанных событий, failures, retries, lag и очередь с существующими логами; параметры согласовать по реальной нагрузке. Не блокировать HTTP уведомлением, если бизнес-операция уже зафиксирована.

Результат: схема жизненного цикла события, гарантии и их границы, тесты rollback/restart/duplicate/concurrency, порядок восстановления.
