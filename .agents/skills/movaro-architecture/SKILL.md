# Architecture

Перед проектированием прочитать docs/architecture.md, AGENTS.md, актуальный issue, реальный граф зависимостей и схемы. Согласованный стек — модульный монолит NestJS/Fastify, PostgreSQL/Prisma, отдельные точки запуска web/admin/api/bot/worker. Не переходить на микросервисы, CQRS/event sourcing, Kafka, Redis или новую ORM по совету внешнего навыка.

- Определить бизнес-термины, ответственность модуля, владельца данных, входные/выходные контракты, инварианты, границу транзакции и права. Разделять логические домены без обязательного создания пяти слоёв на каждую CRUD-операцию.
- Контроллеры и интеграционные адаптеры переводят внешний формат; бизнес-решения принимаются сервисами/вариантами use case. Чистые функции для вычислений. Абстракции/порты добавлять при реальной границе, сменяемой инфраструктуре или тестовой потребности. Не дублировать Prisma API пустым generic repository.
- Экспортировать только нужные публичные интерфейсы Nest-модулей, исключать циклы и общий god-service. Клиенты не ходят напрямую в бизнес-таблицы; bot/worker используют согласованные контракты и серверные операции.
- Инварианты MOVARO: данные компаний изолированы; водитель может работать с несколькими компаниями, но его занятость глобальна; бронирование техники/мест и принятие заявок атомарны; финансы компании не видны глобальному администратору; ставки и расчёты точные, время события UTC, график в часовом поясе объекта. Детали статусов и переходов — из актуальных задач.
- Для крупной функции сначала описать happy path, отказ, конкурентность, повтор, транзакцию и последствия сбоя. Не строить будущие модули заранее. Сравнить минимальное решение с альтернативами, стоимость эксплуатации и обратимость.
- Существенное архитектурное изменение оформлять как предлагаемое ADR: контекст, варианты, решение, причины, последствия, риски, миграция/rollback, issue и статус. Не объявлять новый ADR принятым до согласования. Существующие решения в docs/architecture.md не переписывать без основания.
- На ревью проверить зависимости, типы, границы и тестируемость; применить movaro-database, movaro-security, movaro-api, movaro-async по затронутым контрактам.

Результат: схема границ, контракт и инварианты, список решений/открытых вопросов, план проверок. Источники: https://docs.nestjs.com/modules ; https://github.com/wshobson/agents/tree/main/plugins/backend-development/skills/architecture-patterns .
