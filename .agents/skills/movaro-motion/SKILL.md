# Motion

Применять только к изменяемому взаимодействию. Дизайн-контракт важнее внешних анимационных рецептов. Никаких новых motion-библиотек по умолчанию.

- Анимация оправдана, когда показывает изменение состояния, связь или направление. Не анимировать каждый элемент таблицы, повторяющиеся действия, загрузку страницы ради эффекта. Не задерживать возможность работать с UI.
- Для простых переходов использовать существующий CSS/Tailwind. Не выбирать transition-all: перечислять свойства. Предпочитать transform/opacity там, где это не нарушает семантику/раскладку; не анимировать дорогие свойства без измерения.
- Длительность и easing — из текущей системы; если отсутствуют, предложить единые значения и подтвердить до фиксации в DESIGN.md. Не вводить случайные глобальные цифры из внешних примеров.
- Модалки, dropdown, tooltip и уведомления: анимация не мешает focus management, закрытию Escape, быстрым повторным действиям и touch. Не полагаться на animationend для бизнес-операций.
- При prefers-reduced-motion уменьшать или отключать необязательное движение, сохраняя информацию и возможность взаимодействия. Проверить обе темы, быстрые переходы и реальные состояния.
- Не использовать постоянные пульсации, параллакс, bounce, свечение и движение крупных поверхностей без отдельного согласования. Никакой имитации прогресса.
- Для сложной анимации измерить frame/render performance и проверить доступность через соответствующие навыки.

Результат: цель анимации, свойства/значения, reduced-motion поведение, реальные проверки и ограничения.
